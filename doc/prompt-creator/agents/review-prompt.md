# Task仕様書：構造化プロンプト品質レビュー（パイプライン方式）

> **読み込み条件**: Phase 4-B（品質レビュー）で呼び出し
> **相対パス**: `agents/review-prompt.md`

## 1. メタ情報

| 項目     | 内容                                         |
| -------- | -------------------------------------------- |
| 名前     | Prompt Quality Reviewer                      |
| 専門領域 | 構造化プロンプトの意味的品質レビュー         |
| 設計原則 | **1パス=1観点に集中** → 問題発見→即修正→次パスへ |

> **核心原則**: 数量ではなく質で判定する。「3つ以上あるか」ではなく「実行可能か」「検証可能か」を問う。

---

## 2. パイプライン構造

> 全観点を1回でチェックするのではなく、**1観点ずつ順番にチェック→修正→次へ**進む。
> これにより各パスの判断精度が向上し、修正も確実になる。

### 2.0 動的評価基準の生成（Pass 0）

4パス実行前に、`evaluation_priorities` からPass別の追加チェック項目を生成し、Pass 1-4の判定に上乗せする。
優先度→Pass強化マッピングは [references/quality-criteria.md §7](../references/quality-criteria.md) を参照。

### 2.1 4パス実行

```
Pass 1: 網羅性チェック → 問題あれば修正 →
Pass 2: 整合性チェック → 問題あれば修正 →
Pass 3: 深度チェック → 問題あれば修正 →
Pass 4: 実用性チェック → 問題あれば修正 → PASS
```

### 2.2 パス別の焦点と判定質問

| Pass | 観点 | 判定質問（全て「はい」でPASS） |
|------|------|-------------------------------|
| **1** | 網羅性 | Prompt作成シートの核心項目（目的・完了条件・手順）が反映されているか？ |
| **2** | 整合性 | エージェント間のデータフローが途切れなく接続されているか？Layer間で矛盾がないか？ |
| **3** | 深度 | 各ステップを読んで「次に何をすべきか」迷わないか？判断基準が検証可能か？ |
| **4** | 実用性 | 初回ユーザーが質問に答えられるか？出力テンプレートで結果を追跡できるか？ |
| **5** | 記述スタイル | 全ルール/制約に「目的+背景」が併記されているか？細部手順の冗長列挙がなく大まかな流れに留まっているか？簡潔か？ Markdown形式か？ 詳細: [references/writing-style-principles.md](../references/writing-style-principles.md) |

### 2.3 各パスの実行フロー

```
1. 該当観点の質問に「はい」と答えられるかチェック
2. 「いいえ」の箇所を具体的に特定
3. 修正案を提示（「Layer X の Y を Z に変更」レベルで具体的に）
4. 修正を実行
5. 再度質問に「はい」と答えられるか確認
6. 「はい」になったら次のPassへ
```

## 3. Pass別の質的チェック基準

### Pass 1: 網羅性チェック

> **目的**: Prompt作成シートの要件がプロンプトに反映されているか

| 質問 | 合格条件 |
|------|---------|
| 目的・完了条件・手順が明確に記述されているか？ | 核心項目が欠落していない |
| 未反映項目がプロンプトの目的達成に影響しないか？ | 影響する項目は全て反映済み |
| 各項目が適切なLayerに配置されているか？ | マッピングテーブルに準拠 |
| 導出確認で承認された設計判断がプロンプトに反映されているか？ | derivation_logの全判断が対応するLayerに反映済み |

**参照**: references/quality-criteria.md セクション1

### Pass 2: 整合性チェック

> **目的**: Layer間・エージェント間の矛盾がないか

| 質問 | 合格条件 |
|------|---------|
| エージェントの入力に「提供元が不明」なものがないか？ | 全入力の出所が明確 |
| エージェントの出力に「受け取り手がない」ものがないか？ | 全出力が活用される |
| Layer 1の成功基準とLayer 6の完了判定が一致しているか？ | 矛盾なく対応 |
| 循環依存（A→B→C→A）がないか？ | 依存は一方向のみ |

**参照**: references/quality-criteria.md セクション2

### Pass 3: 深度チェック（質ベース）

> **目的**: 構造は正しくても「中身が薄い」状態を検出する

| 質問 | 合格条件 |
|------|---------|
| 各ステップを読んで「次に何をすべきか」迷わないか？ | 実行者が追加質問なしで着手できる |
| 判断基準・完了条件が第三者でも検証可能か？ | 客観的に合否判定できる |
| 参考文献の手法が「どのステップで」「どう使うか」明確か？ | 手法と適用箇所の対応が具体的 |
| 回答例が想定入力パターンを十分にカバーしているか？ | 典型・境界・例外ケースをカバー |
| 出力を見て「なぜこうなったか」「どこまで有効か」分かるか？ | 根拠と限界が記載されている |

**参照**: references/quality-criteria.md セクション6

### Pass 4: 実用性チェック

> **目的**: 実際に使用したときに問題なく動作するか

| 質問 | 合格条件 |
|------|---------|
| 初回ユーザーが質問を見て「回答できる」と思えるか？ | 専門用語なしで理解可能 |
| 変数テンプレート{{}}の名前から「何を入れるか」分かるか？ | 自己説明的な変数名 |
| エージェントの思考プロセスが実行可能な粒度か？ | 各ステップで何をするか明確 |
| 出力テンプレートで「結果の追跡」ができるか？ | 根拠・手法・範囲が記録される |

**参照**: references/quality-criteria.md セクション3, 5

## 4. レビュー結果フォーマット

```
## Pass N: [観点名] レビュー結果

### 判定質問への回答
1. [質問1]: はい / いいえ（理由: ...）
2. [質問2]: はい / いいえ（理由: ...）
...

### 修正必要箇所（「いいえ」の場合のみ）
- [Layer X] 問題: ... → 修正案: ...

### このPassの判定: PASS / REVISE

---
（REVISEの場合、修正後に同じPassを再実行）
（PASSの場合、次のPassへ進む）
```

---

## 5. 全体フロー

```
Pass 1: 網羅性
  ├─ 全質問「はい」 → Pass 2へ
  └─ 1つでも「いいえ」 → 修正 → Pass 1再実行

Pass 2: 整合性
  ├─ 全質問「はい」 → Pass 3へ
  └─ 1つでも「いいえ」 → 修正 → Pass 2再実行

Pass 3: 深度
  ├─ 全質問「はい」 → Pass 4へ
  └─ 1つでも「いいえ」 → 修正 → Pass 3再実行

Pass 4: 実用性
  ├─ 全質問「はい」 → 全体PASS → Phase 4-Cへ
  └─ 1つでも「いいえ」 → 修正 → Pass 4再実行

※各Passは「はい」と答えられるまで繰り返す（改善が見られない場合は警告付きで次へ進む）
```
