## AI エージェントから「再現性のある出力」を引き出すには、どうすればいいのか。

これは Claude Code を仕事で使っている人が、どこかで一度はぶつかる問いです。

毎回プロンプトを書き直す段階を超えて、決まった品質で同じ作業を呼び戻したい。レビュー、画像生成、スライド作成、調査、評価。「その時の調子」ではなく、「呼べばこの品質で返ってくる」 状態にしたい。

Claude Code の Skill は、ここに対する有力な答えのひとつです。

そして、ここからが本題です。

Skill は実のところ、単なる「プロンプトの保存場所」では止まりません。

複数の Skill を組み合わせていくと、エージェントの上に 小さなアプリのような構造 が組み上がります。

事実上、オーケストレーションスキル と呼ぶべき領域です。Claude Code を「賢いチャット相手」から「再現可能な業務システム」に変える可能性が、ここに眠っています。

ただし、全員がここで同じ壁にぶつかります。

道具と仕様だけはある。でも、それを設計するための言語がない。

Skill を 1 本書くだけなら難しくありません。けれど、複数の Skill を組み合わせた"アプリ"を育てていこうとすると、すぐに迷います。

何を 1 つの Skill にまとめ、何を切り出すべきか

どの Skill に何を任せ、何を任せないか

任せた仕事の品質を、誰がどうやって判定するのか

増えてきた Skill 群を「アプリらしさ」を保ったまま、どう進化させていくか

これは「プロンプトのコツ」では解けません。
解けないまま進めると、複雑なものを複雑なまま積み増していくことになり、ある瞬間から、進化させるのも作るのも現実的にしんどくなります。

## この記事は「発明と概念提唱の報告」です
そこでこの記事は、Skill のノウハウ集としてではなく、私が実運用の中で発明・提唱してきた概念をまとめて報告する形にしました。

公式仕様の翻訳ではありません。Claude Code 公式が示しているのは、Skill とは何か / どこに置くか / どう動かすか、までです。

本記事ではそれを土台にしつつ、

Skill の責務をどう切り分けるか

完了判定をどこに置き、誰に判定させるか

オーケストレーション全体を、どう「設計可能な部品群」として扱うか

これらに対して、自分が運用してきた数百本の Skill から抽出した 新しい概念をいくつも提唱しています。

ただしこのリード文では、発明した概念のラベル自体は出しません。
理由はシンプルで、ラベルだけ先に渡されても使えないからです。

実物の Skill に当てはめる順番を間違えると、かえって設計が濁ります。本文では、その順番ごと提示ます。

本文ではまず、Claude Code の公式仕様を整理します。そのうえで、Skill を作る前にどこで解くべきかを判断する基準、入口と本文の薄め方、増えた Skill 群を整理する規範、「できました」を信用せずに品質を機械的に判定する仕組みまで降ります。

最後に、実物の `SKILL.md` を題材にした解剖を置きました。

対象読者は、すでに Claude Code を触っていて、Skill を「便利なプロンプト集」以上のものにしたいと感じている人です。

「なんとなく便利」から、「呼べばこの品質で返ってくる」へ。
「便利な小道具」から、「育てられるオーケストレーション」へ。

その移行に必要な設計言語を、この一冊にまとめました。

## この記の位置づけ
この記事はこんな読者のために書ている:

Skill を作り始めたが、どこまでを 1 つの Skill にまとめるべきか迷っている。

`description`、名前、frontmatter、本文に、それぞれ何を書ばよいか整理したい。

「参照資料」「実行手」「ラッパー」「評価器」「委譲」のような割ごとに、Skill を組み立てる基準が欲しい。

来 Skill が増えても、命名・責務・評価が破綻ない形で最初から設計したい。

生成器と評価器を分けたいが、どこまで分ければ運用として味があるか判断したい。

本記事で扱うのは、Skill の数を増やすテクニックではない。
Skill を「なんとなく便利なプロンプト」から、責務を持った部品として組み立てるための概念整理である。
この整理があると、1 個目の Skill も書きすくなるし、結果として大量の Skill を運用する段階でも破綻しにくくなる。

重要なのは、Skillの数というよりも、どの複雑さに向き合っているかである。

1 個でも責務が重ければ評価設計が必要になるし、20 個あっても単純な参照資料けなら軽い規約で足りる。

Skill 群を設計可能な資産に変えるための規範体系 — 4 軸分類、5 prefix 決定木、評価駆動 (generator / evaluator 分離) 、まず概念として整理する。

## この記事で持ちるもの
Skill は「プロンプトの断片」ではなく、エージェントが読みに来る再利用部品として設計する。

Skill を作る前に、まず Skill / Subagent / Hook / 実装層 (MCP / CLI / API) のどこで解くべきかを判断する。

Skill の命名は感覚で決めない。4 軸を埋めれば、prefix は概ね機械的に決まる。

ワークフロー型 Skill は「できました」で終わらせない。生成役と評価役を別 Skill に分け、外部評価器で完了を判定する。

## Part 1. 公式仕様を正しく押さえる
### 1. なぜ Skill が必要なのか
この章の核: Skill は、長くなったプロンプトを分割するための小技ではない。チームに散らばった運用知を、再利用できる業務部品として扱うための仕組みである。

結論から言うと、Skill は AI 活用のノウハウを「個人のプロンプト術」から「チームで運用できる資産」に変える。

生成 AI の活が進むと、最初に効いてくるのはモデル性能の差ではない。むしろ問題になるのは、うまく使うための知識が散らかることである。

最初は 1 枚のプロンプトで足りる。

しかし、現場で使い続けるうちに、そこへ業務ルールが少しずつ足されていく。

このリポジトリでは、この規約従う

PR レビューでは、この観点を見る

デプイ前には、この順序で確認する

このツールは自動承認し、この操作は確認を挟む

こうした運用知識をすべて `CLAUDE.md` や system prompt に詰め込むと、やがて編集不能な巨大文書になる。

巨大プロンプトには、分かりやすい限界がある。

新しい規則を足すたびに、別の挙動が変わる

タスクに関係のない情報まで、毎回モデルに読ませる

どの指示が、どの成果に効いているのか分からない

属人的な「秘伝のプロンプト」になり、チームで改善できない

これは単なるプロンプト管理の問題ではない。

業務で使う知識が、まだ 部品化されていない という問題である。

Claude Code の Skill は、この問題に対する 1 つの答えである。

Skill を使うと、LLM に読ませる知識や手順を、用途ごとに切り出せる。

PR レビュー用の Skill

デプロイ確認用の Skill

障害調査用の Skill

ドキュメント作成用の Skill

評価・採点用の Skill

それぞれに名前を付け、責務を決め、必要なときだけ呼び出す。すると、プロンプトは「長い一枚岩」ではなく、組み合わせ可能な部品群になる。

![[Obsidian 2026-05-17 15.14.41.png]]
Skill は `SKILL.md` を中心に構成される。Claude は関連すると判断したときに Skill を使い、ユーザーも `/skill-name` で直接呼び出せる。

重要なのは、Skill 本文が常時ロードされるわけではないという点だ。使われたときだけ読み込まれるため、長い参照資料や手順書を、必要になるまでほぼコストなく置いておける。

なお、Claude Code Skills は Agent Skills open standard に準拠し、Claude Code 側で呼び出し制御・subagent 実行・動的コンテキスト注入などを拡張している。

ビジネス視点で見ると、Skill の価値は大きく 3 つある。

品質を安定させる — 毎回その場で指示を書くのではなく、検証済みの手順を再利用できる。

知識を共有資産にする — 個人のプロンプトではなく、チームで読めて直せる形にできる。

変更に強くする — 1 つの巨大プロンプトを触るのではなく、対象の Skill だけを更新できる。

つまり Skill は、LLM における「関数」や「コンポーネント」に近い使い方をすることもある

ただし、Skill を増やせば自動的に整理されるわけではない。関数名が雑ならコードベースが読めなくなるのと同じように、Skill も設計規範なしに増やすと破綻する。

必要なのは、単にプロンプトを分割することではない。次の 3 つを決めたうえで、Skill を部品として扱うことだ。

何のための Skill か — 知識注入なのか、作業手順なのか、評価なのか。

いつ呼ばれるべきか — モデル判断で呼ぶのか、ユーザーが明示するのか、別コンテキストへ逃がすのか。

何を返すべきか — 説明、成果物、検証結果、次のアクションのどれなのか。

本記事の主張はシンプルだ。

Skill は勘で書く文書ではない。設計し、命名し、検証する部品だ。

### 2. Claude Code の拡張点と実装層 — Skill / Subagent / Hook / MCP

![[Pasted image 20260517151648.png]]
この章の核: Skill は道具ではなく、道具の使い方を書く 1 段上のレイヤーである。Claude Code には Skill 以外に Subagent / Hook / MCP があるが、これらは同じ種類の部品ではない。

Skill / Subagent / Hook は主に 運用を制御する層、MCP は CLI / API と並ぶ 外部接続・実装層 に近い。本章はまずそのズレを整理し、章末の補論で「Skill = メタ層」という根源的な視点を扱う。

Skill を語る前に、Claude Code には Skill 以外の拡張点があることを押さえる必要がある。Skill に何でも詰め込むと、設計を誤る。

ただし、ここで注意が要る。

`Skill / Subagent / Hook / MCP` は Claude Code の機能一覧としては並べられるが、設計レイヤーとしては同列ではない。

大まかには、次のように分けて見る方が分かりやすい。

![[Pasted image 20260517151701.png]]
この表だけを見ると 4 つが横並びに見えるが、設計上は次の層構造で捉える方がよい。

![[Pasted image 20260517151710.png]]
つまり MCP は少し特殊である。

Claude Code の機能一覧では Skill / Subagent / Hook と並ぶ 拡張点 だが、設計上は CLI / API と並ぶ 外部接続の実装手段 でもある。ここを混ぜると、「Skill と MCP のどちらで作るか」という問いが曖昧になる。

ここでの基本方針はこうだ。

決定論で組めるものは、まず決定論システムに逃がす。lint、format、schema validation、禁止語チェック、API 呼び出し、DB 更新のように機械で確実に処理できるものを、自然言語の Skill に戻さない。

Skill を高級リンターにしない。毎回同じ規則で落とせる検査は Hook / CI / CLI / MCP / API に寄せる。Skill は「どの検査をいつ使うか」「結果をどう解釈するか」に集中する。

Skill は使い方を書く場所。外部 API や DB 接続の実体は MCP / CLI / API に寄せる。

毎回必ず走るものは Hook。LLM が思い出すかどうかに依存させない。

独立判断が必要なものは Subagent。同一コンテキストで抱え込まない。

MCP は agent 向けの意味単位を作る場所。外部 API をそのまま露出するだけでなく、操作・参照・型 prompt を agent が扱いやすい粒度に包める。

Skill は横断的な運用方針を束ねる場所。どの MCP / CLI / API を、どの順序で、どのチーム方針に沿って使うかを整理する。

Skill は他の実行手段を束ねる指示書にもなる。MCP の使い方、CLI の叩き方、Subagent への委譲、Hook の前提を Skill 側で整理できる。

![[Pasted image 20260517151722.png]]
上の決定木が示すように、Skill を作る前にまずこう問う。

これは本当に Skill に書くべきか。決定論で組めるなら Hook / CI / CLI / MCP / API に逃がすべきではないか。独立コンテキストが要るなら Subagent ではないか。

この問いを飛ばすと、Skill はすぐに「何でも屋」にな。特に危ないのは、Skill を「賢いチェックリスト」や「高級リンター」として使い始めることだ。

チェック対象が機械的に定義できるなら、Hook や CI で落とす。CLI や API で確実に取れる値なら、それを取る。MCP で schema 付きの tool として渡せるなら、その形にする。Skill は最後に残る 文脈依存の判断 と 複数手段の使い分け を扱。

実装層 (CLI / MCP / API) のどれを選ぶかは、実行環境 にも左右される。ローカルの Claude Code のように shell が使える環境なら、`git` / `gh` のよな既存 CLI を直接叩くのが最も速い。公式 CLI が無くても API があれば、Peter Steinberger 流に薄い自作 CLI ラッパーを書く手が効く。

MCP が要るのは shell を持たないクラウドエージェント、各自に CLI を書かせずチームに配布したい場面、複雑な外部 API を agent 向けの意味単位で渡したい場面だ。同じ機能を CLI と MCP の両方で抱えないのが原則だが、どちらを採るかは環境制約で決まる。

実装層 (CLI / MCP / API) を厚く整え、その上に Skill レイヤーで「使い方」を整理する。3 者は同じレイヤーを取り合っているのではなく、役割が違う (この層構造の根拠は次の補論で深掘りする)。

これらはすべて 「道具そのもの」 である。LLM がボタンを押せる対象。

そして Skill は、これらの道具の「使い方」を書く場所 だ。

同じ `gh` CLI を叩くにしても、「PR レビューのときはこうする」「リリース前はこの順番で」という 使い方の型 を Skill 本文に書く。Skill 自体は道具を実装しない。道具を いつ・どう・なぜ 使うかをエージェントに伝える、1 つ上のレイヤー である。

![[Pasted image 20260517151812.png]]
この層構造が見えると、いくつかの判断が機械的になる。

決定論で書ける処理は Skill に書かない。自然言語で説明するより、Hook / CLI / API / MCP tool にした方が確実で、速く、トークンも使わない。

同じ機能を CLI と MCP の両方で抱えない。ただし CLI と MCP のどちらに寄せるかは 実行環境次第 だ。shell が使えるローカル Claude Code なら既存 CLI (`git`, `gh`, `rg`, ...) を直接叩く方が速い。

公式 CLI が無くても API があれば薄い自作 CLI ラッパーで十分 (Peter 流)。shell の無いクラウド agent や、各自に CLI を書かせずチームに配布したい場面では MCP が必要になる。

重複を持つ前に「この環境ではどちら一本に絞れるか」を問う。

Skill 同士が同じ道具を別の使い方で叩くのは正常。`run-pr-review` と `run-release-checklist` が両方とも `gh` を叩いてよい。

Skill 本文に道具の挙動を書きすぎない。それは実装層側の責任。Skill は「うちのチームではこう使う」という運用知識に集中する。

### CLI 派と、それを包摂する Skill 派
![[Brave Browser 2026-05-17 15.19.55.png]]
この CLI 層への倒し方を強く推している人物として Peter Steinberger (steipete, openclaw開発者) がいる。彼は「mcp were a mistake. bash is better.」と発言し、AI に MCP のような重い抽象を被せるより、生の CLI を直接叩かせる運用を推している。

事例として、彼が公開している artifact をいくつか並べる。

`gogcli` — Gmail / Calenda など Google Workspace の主要サービスを 1 つの binary で叩ける CLI (`brew install steipete/tap/gogcli`、JSON-first 出力)。Google には API も MCP の選択肢もあるが、実装は CLI 1 本に倒している。

Peekaboo 2.0 — 元は Swift CLI + 薄い TypeScript の MCP ラッパー構成だった OSS が、2.0 で CLI 主導に逆転、MCP を optional の薄ラッパーへ格下げ。タイトルは "Freed from its MCP shackles"。

`mcporter generate-cli` — 任意の MCP を self-contained な bun CLI に変換する CLI。

CLI に倒す根拠としてしばしば挙げられるのは、次の 3 つの工学的事実だ。

トークン効率 — MCP は tool schema を会話の冒頭でモデルに読ませる必要がある。重い構成では 100k トークン規模が「tool 定義の表示料」として 1 会話ごとに乗ることが報告されている。CLI は `--help` を on-demand で読めばよく、使わない道具のコストが context に乗らない。

コンポーザビリティ — bash パイプは推論を挟まずに 5 段でも 10 段でも繋がる。MCP の 5 ツール連結は推論を 5 回挟むので、その分トークンも時間も食う。

再現性 — bash は標準入出力で再現できる。AI 専用の接続層を経由しない分、人間が同じコマンドを叩けばそのまま動く。

ここまでが「CLI を作って渡す」という実装層側の話だ。本記事の関心はこの一段上にある。

Skill の公式リリースは、枠として「Claude にスクリプトを使わせる正式な道」のアナウンスだった。しかしスクリプトは育つ。
本数が 3 つを超えるあたりから共通処理が見え、API キーを 1 か所に置きたくなり、トークン更新の state を抱えたくなり、config を持ちたくなる。

### この瞬間、スクリプトは「小さなアプリ」になりたがる。

僕も自らアプリ化するSkillをいくつも作ってきたので、これを強く思っています。(例: remotion動画作成など)

ここで CLI への昇華が効く。認証も `--help` 面も内部状態も CLI 側に閉じ、Skill 本文には「うちでは `gog` を叩く」とだけ書けば済むようになる (具体的な昇華パスは次節で扱う)。

そしてもう 1 つ、見過ごされがちな追い風がある。バイブコーディング、CLI を 1 本立ち上げるコストを劇的に下げたAPI があるなら薄い CLI を巻くのが最短になった、という時代条件だ。

先に挙げた `gogcli` / Peekaboo の MCP→CLI 反転 / `mcporter` も、この追い風の上に乗っている事例として読める。

こう辿り直すと、「CLI 派 vs MCP 派」の論争は やや浅い場所で起きている ことが分かる。本当に動いたのは「スクリプトを CLI に育てるコスト」の方で、それが下がったから CLI が選ばれている。

スクリプトが小さなアプリに育つ瞬間に CLI で受け止るのが最低コスト これが本記事の見ている工学的事実だ。

その上で、本記事の立場は以下の通り

CLI も MCP も「道具」。Skill が両方を包摂する「使い方」のレイヤー
対立ではなく、レイヤーが違う。

この層構造で再配置すれば、議論はこう整理される。

道具は CLI で薄く作る。bash で叩けて、人間も使えるツールを増やす。

MCP が必要な場面では MCP を使う。schema が固い場面、リモート実行、shell の無いクラウドエージェント、CLI を各自に書かせずチームに配布したい場面など。

「いつどちらをどう使うか」は Skill に書く。エージェントが読みに来るのはここ。

「道具の作り方」と「道具の使い方」は別レイヤーの問題で、両者は補完関係にある。CLI が実装層を薄く整え、MCP が「クラウド・配布が要る場面の標準プロトコル」を担い、Skill レイヤーが両者の 使い方 を整理する。

本記事が一貫して扱うのは、この 使い方 のレイヤーだ。

実装層の中にも階層がある 既存 CLI / スクリプト / 自作 CLI の昇華パス
ここまで「実装層 (CLI / MCP / API)」を 1 枚岩のように扱ってきたが、ローカル shell 環境で実装層を組むときは、その内側にもグラデーションがある。低コストな順に並べると次の 4 段だ。

![[Pasted image 20260517152051.png]]
既存 CLI を組み合わせる: `git` / `gh` / `rg` / `jq` をパイプや `&&` で繋ぐ。最も軽く、依存も増えない。Peter 流の入口はここ。

薄いスクリプトを書く: Bash / Python の短いスクリプトに固める。手順が 3 ステップ以上、あるいは条件分岐や I/O 整形が要るときに昇格する。スクリプト自体は CLI ラッパー化していないので、API キーや初期設定は呼び出し側が毎回渡すことになる。

自作 CLI に昇華する: スクリプトが増えて共通処理が見えてきたり、API キー / 認証情報を扱いたくなったり、内部状態 (軽量 DB / cache / config) を持たせたくなったら、ちゃんと CLI に育てる。

自作 CLI を既存 CLI と組み合わせる: 作 `mytool` と `gh` / `rg` をパイプで繋ぐ。Skill 本文には「うちでは `mytool` と `gh` をこの順で叩くという使い方の型だけを書く。

自作 CLI に昇するメリットは大きい。

AI agent フレンドリーな目的ベース API 面を生やせる。`mytool deploy --env staging` のように「やりたいこと」を 1 行で表現できる。`--help` も 1 か所に集約され、agent が試行錯誤しやすくなる。

API キー / 認証情報を CLI 内部に隠せる。`mytool login` で 1 回保存、以後はび出し側が意識しなくていい。スクリプトのせ集めだと毎回環境変数を引き回すことになりがち。

軽量 DB / cache を内側に抱えられる。SQLite や JSON store を持てば「直前の実行結果」「キッシュ済みデータ」を CLI 側で覚えさせられるSkill 本文に状態管理を書かずに済む。

小さなアプリケーションとして振る舞える。単発スクプトの寄せ集めから「再利用可能な小さなアプリ」に格上げされる。

メンテコストは確かに増える。ただ AI 駆動開発で巻き取れる範囲が広がっているので、自作 CLI を持つ閾値はどんどん下がっている。判断の目安はこうだ。

スクリトが 2-3 本以上に増え、共通処理が見えてきた

API キー / 認証情報を扱う必要が出てきた

内部状態 (キャッシュ / 履歴 / 設定) を持たせたい

このいずれかが当てはまったら、スクリプトの寄せ集めから自作 CLI へ昇華するタイミング だと考える。Skill 側はその昇華に追従して「以前は `script.sh` を叩いていたが、いまは `mytool` を叩く」と書き換えるだけで済む。実装層が分厚くなるほど、Skill 本文は薄くなる。

## 3. SKILL.md の基本 — description は人間向け要約ではない
![[Pasted image 20260517152110.png]]
公式仕様では、すべての Skill は `SKILL.md` を持つ。基本形は次の通り。

---
name: explain-code
description: Explains code with visual diagrams and analogies. Use when explaining how code works, teaching about a codebase, or when the user asks "how does this work?"
---

When explaining code, always include:
1. Start with an analogy
2. Draw a diagram
3. Walk through the code
4. Highlight a gotcha

copy
`SKILL.md` は大きく 2 つに分かれる。

![[Pasted image 20260517152123.png]]
特に重要なのは `description` である。

`description` は人間向けの紹介文ではない。Claude が「この Skill を読むべきか」を判断するためのトリガー条件である。

悪い例:

description: スキルレビュー機能。スキル設計を採点するためのスキルです。

copy
良い例:

description: Skill 設計の評価器。「skillレビュー」「SKILL.md採点」で発動。

copy
人間向けに自然な文より、モデルが発動条件を判断しやすい文を書く。

2 つの落とし穴 — 動作の手順を説明してしまう / 発動ワードを並べすぎる
description を「発動条件」に倒すとき、初手で踏みやすい落とし穴は 2 つけだ。

落とし穴 1: 動作の手順を説明してしう

description に動作の流れや手順を書くと、Claude は 本文を読まず description の短縮版だけで動。

obra/superpowers の writing-skills が報告した事例は、description に `code review between tasks` (「タス間のコードレビュー」という意味) と書いた Skill が、本文のフローチャートでは「仕様準拠レュー → コード品質レビュー」という 2 段の処理を予定していたにもかかわらず、Claude は 1 段しか実行しなかった。description を `Use when executing implementation plans with independent tasks` (「独立したタスク実装の計画を遂行するとき」= いつ呼ぶか、だけ) に直したら、本文を読み 2 段レビュー正しく実行した。

したがって description は いつこの Skill を呼ぶべきか だけに絞り、呼ばれてをするか (手順・段数・形式) は本文で展開する。「採点する」「JSON で返す」「複数段の並列実行」のような動詞・処理の流れ・段数は description に出さない。

落とし穴 2: 発動ワードを並べすぎる

`「skillレビュー」「スキル設計の採点」「SKILL.mdの評価」で発動` のように 3 個以上並べたくなるが、上限は 2 個前後 で十分だ。3 個以降は次のどちらかに化けやすい。

(a) 重複  「スキル設計の採点」「SKILL.mdの評価」のよに、ほぼ同じ意味の言い換え

(b) 処理の流れが紛れ込む — 「複数パターン」「JSON で返す」のように、どう動くかの説明が混ざり込む (落とし穴 1 と同根)

発動ワードを並べるほど description 全体が長くなり、`description` + `when_to_use` の合算が 1,536 文字に制限される点や、Skill 一覧全体がコンテキスト予算に収まる必要がある点を圧迫る。2 個ルール は冗長さを削る目安として覚るとよい。

3 タイプで Before / After を並べる
「人間向け要約」と「発動条件」の差は、prefix が違っても同じ形で再現する。読み手が自分の Skill に当てはめられるよう、3 タイプで並べてお。

![[Pasted image 20260517152140.png]]
3 例に共通する破綻パターンは次の 3 だ。

発動ワードがない、または多すぎる — Claude がユーザー発話と照合するための「鍵」が description にない、または 3 個以上並べて (a) 重複が生じている、もしくは (b) どう動くかの説明が紛れ込んでいる

役割・派生元・採点根拠が見えない — `assign--evaluator` なら何の ref を根拠とするか、`wrap-` なら何の base を呼び出すかを、説明文ではなく frontmatter の 1 行で示すべき

動詞や手順で動作説明が混じっている — 「採点する」「JSON で返す」「4 枚並列実行する」のように動詞や段数を書くと、Claude は本文を読まず description の短縮版だけで動く

逆に言えば、description を書き直すときの作業はこの 3 点を埋めるだで済む。文章を膨らませる必要はない。

公式様上、`description` と `when_to_use` の合算は skill listing 内で 1,536 文字に切られる。さらに Skill が多い場合、description 群全体もコンテキスト予算に収めるため短縮される。だから description は短く、先頭に核心を置く。

### Claude Code Skill の frontmatter
![[Pasted image 20260517152159.png]]
ここで扱う frontmatter は Claude Code の Skill 仕様 に固有である点に注意してほしい。`name` / `description` のように一見汎用的なフィールドはともかく、`context: fork` (forked subagent context での実行)、`disable-model-invocation`、`user-invocable`、`allowed-tools`、`agent`、`shell` などは Claude Code が Skill 機構として独自に拡張したフィールドだ。

他の開発系 AI エージェント (Cursor / Cline / Codex CLI など) 同じ仕組みがあるとは限らないため、Skill ファイルをそのまま別エージェントに持ち込んでも同じ挙動にはならない。

特に `context: fork` は本記事でも繰り返し登場するキー機構なので、Claude Code 固有の仕掛けである点は意識しておくとよい。

特に誤解しやすいのは `allowed-tools` だ。これは「このツールだけ使える」という禁止設定ではない。列挙したツールを承認なしで使えるようにする allow-list であり、未列挙ツールの可否は通常の permission settings に従う。書き込みを本当に止めたいなら、permissions 側で deny rule 置く。

## 呼び出し制御の整理
![[Pasted image 20260517152444.png]]
![[Pasted image 20260517152451.png]]
disable-model-invocation: trueは Claude の自律発動だけでなく、親 Skill が `Skill(child)` で呼ぶ経路も同じ拒否で弾かれる。description 自体も context に常駐しない。代わりに残るのは `/skill` 直叩きと、別 Skill が SKILL.md を Read で読み込む経路だけ。

これら 2 つは 意図して設定する フラグであり、起動経を明示的に絞り込むのが目的だ。

`disable-model-invocation: true` は Skill tool 経由の invocation を全部止める。Claude の自律発動も、親 Skill が `Skill(child-skill)` で呼ぶ経路も、どちらも `cannot be used with Skill tool due to disable-model-invocation` で拒否される。

description も context に常駐しなくなる。残る経路はユーザーが `/skill` で直接叩くか、別の Skill が Read で SKILL.md を読み込む (= `ref-*` 辞書の使われ方) だけ。

副作用の大きい手動 Skill (`/ultrareview` のような重い課金処理) や、Read 経由でしか参照されない knowledge Skill に使う。

`user-invocable: false` は ユーザー起点のスラッシュコマンド入力を塞ぐ。Claude や親 Skill からは `Skill()` 経由で引き続き呼べる。`assign-*` 系の sub-evaluator / sub-generator のように内部参照専用にしたい Skill や、別の入口経由でしか呼ばせたくない Skill に使う。

つまり `user-invocable: false` は「ユーザーから見えにくくする」設定であって、Claude から完全に隠す設定ではない。
Claude からも隠したい場合 `disable-model-invocation: true` を併用するか、permissions 側で Skill tool を制御する。

ただし `assign-*` 系のように 親 Skill から `Skill()` で呼ばれる前提 internal Skill に `disable-model-invocation: true` を付けてはいけない。両フラグを併記すると Skill tool 由がすべて弾かれ、`/skill` 直叩きも閉じているため、結果として「誰も呼べない Skill」になる。

`disable-model-invocation: true` が安全に効くのは、Read 経由でしか参照されない `ref-*` 系 (description を context から外す最適化として) と、ユーザー意図的に `/` で起動する手動 Skill だけだ。

## 4. Progressive Disclosure — 必要な時に必要なだけ読まる
![[Pasted image 20260517152506.png]]
本章では、SKILL.md 本文の設計原則である Progressive Disclosure (段階的開示) を扱う。Anthropic 自身も、これを Skills の中核原則としている。

Progressive Disclosure は、単なる「ファイル分割のテクニック」ではない。要点は、必要な情報を、必要になった段階でだけ読ませる ことにある。

この考え方が腹落ちしていないと、判断が毎回ぶれる。何を SKILL.md 本文に残すのか。何を補助ファイルに逃がすのか。500 行未満という目安を、どこまで守るべきなのか。これらを判断するには、まず「なぜ分けるのか」を理解する必要がある。

元の概念は UI/UX にある
progressive disclosure は、もともと UI/UX の考え方である。意味シンプルだ。

最初の画面には、今すぐ必要なものだけを出す。
詳細設定や特殊な選択肢は、要になったときに開けるようにする。

たとえば、アプリの設定画面で、全項目を最初から 1 面に並べると使いにくい。ユーザーは何を触ばよいか分からなくなる。だから、よく使う項目を先に出し、詳細設定は奥に畳む。

Anthropic は、この UI の考え方を Skill 設計に持ち込んだ。対象は画面ではなく、モデルの context である。

SKILL.md にすべての説明、例、仕様、注意事項を最初から詰め込むと、モデルは一見たくさんの報を持っているように見える。しかし実際には、重要な指示が埋もれ、関係ない情報まで判断に混ざる。

つまり問題は、「情報が足りないことだけではない。最初から情報を見せすぎること も問題になる。

だから Skill では、最初に読む SKILL.md には最小限の判断材料だけを書く。詳しい仕様、長い例、補足資料は、必要になったときに読める場所へ分ける。これが Skills における Progressive Disclosure である。

### 3 層に分けて設計する
![[Pasted image 20260517152518.png]]
Skills の段階的開示は、「最初から見えている情報」と「必要になってから読む情報」を分ける設計である。具体的には、次の 3 層で考えると分かりやすい。

![[Pasted image 20260517152529.png]]
入口情報は、セッション中ずっと常駐する。例外は `disable-model-invocation: true` を立てた Skill で、この場合は description が context に入らない。

Skill が 30 個あれば、30 個分の description が並ぶ。ただし、Skill 1 個あたりの入口情報は数十 token 程度に抑えられる。一方で、GitHub MCP はサーバ 1 つで数万 token を使うことがある。桁が 2〜3 違うため、入口情報を短く保てれば Skills のスケール優位は崩れにくい。

ここで §3 の「description を短く、正確に書く」という規律が効いてくる。SKILL.md 本文が読まれるかどうかは、入口情報の精度で決まる。本文をどれだけ磨いても、description が曖昧なら、その Skill は必要な場面で発動しない。

SKILL.md 本文と補助ファイルの境界も重要だ。補助ファイルは、Claude が必要だと判断したときに 能動的に Read しに行く 前提で置く。つまり設計者は、すべての情報を SKILL.md に詰め込む必要はない。SKILL.md には、必要になったときに補助ファイルへ辿れる地図を書く。

### なぜ分けるのか — 全部 SKILL.md に書くと何が起きるか
![[Pasted image 20260517152540.png]]
なぜ、わざわざ SKILL.md と補助ファイルを分けるのか。

理由は単純で、モデルの注意力は有限 だからである。

context window が大きくなっても、そこに入れた情報をモデルが均等に使えるわけではない。長い文章の中に重要な情報を置くと、位置によって使われやすさが変わる。特に中央付近の情報は落ちやすい。これは lost-in-the-middle と呼ばれ、長文 context の研究でも確認されている。

もう 1 つ重要なのが context rot である。これは、context が長くなるほど、関係ない情報や古い前提が混ざり、モデルの判断が鈍る現象を指す。情報は、context に入れた瞬間に中立な背景知識になるわけではない。関係ない情報でも、モデルの attention を奪う。

つまり問題は「context に入るか」ではない。

入れた情報を、必要な場面で、正しく使えるか。

ここが問題になる。SKILL.md に全部を書く設計は、この前提を外している。読ませる量を増やせば賢くなるのではなく、重要なものが埋もれ、関係ないものが判断に混ざる。

全部を SKILL.md に書くと、具体的には 3 つの問題が起きる。

(1) Context 予算が早い段階で消費される。
SKILL.md 本文が大きい Skill は、発動した瞬間に数千 token を使う。長い実装作業の途中で重い Skill がいくつも発動すると、コードを書くための context 予算が先に削られる。

これは、その Skill だけの問題ではない。SKILL.md に書いた一行は、他の Skill や後続タスクの予算とも競合する。HumanLayer の Kyle は、この予算感覚を instruction budget と呼んでいる。

(2) 重要なルールが中盤に埋もれる。
長い context の中央に置かれた指示は、モデルが読み落としやすい。先ほどの lost-in-the-middle が、そのまま Skill 本文にも効く。

SKILL.md 本文が肥大化すると、最も重要な禁則事項が本文の中盤に沈む。`NEVER` と書いたのに守られない、という事故の一因はここにある。重要なルールど、本文の冒頭で見える位置に置く必要がある。

(3) 無関係な情報が判断を歪める。
読まれない情報は、完全に無害ではない。タスクに関係のない参照情報でも、context に載っていれば attention を奪う。これが context rot の実務上の怖さである。

長い表、詳細仕様、大量の例は、必要な場面では価値がある。しかし常に SKILL.md 本文に置くと、判断のノイズになる。だから補助ファイルに降ろす。

入口情報 / SKILL.md 本文 / 補助ファイルを分ける目的は、見た目の整理ではない。有限な attention を、今必要な情報に向けるため である。

結論として、設計者がやるべきことは 3 つに絞れる。

SKILL.md 本文を短く保ち、context 予算を先に使い切らない。

最重要ルールを SKILL.md 本文の冒頭に置く。

長い参照情報や低頻度の情報は補助ファイルに降ろす。

推奨構造 — 本文には案内だけを書く
公式が示す推奨ツリーはこうだ。

my-skill/
├── SKILL.md           # 入口。発動条件・最小手順・重要な注意
├── reference.md       # 詳細仕様、長い表、API リファレンス
├── examples/
│   └── sample.md      # 入出力例
└── scripts/
    └── validate.sh    # Claude が実行できるスクリプト

copy
ファイル名は規約として強制されているわけではない。公式例には `template.md` を置くものもあるし、`forms/` や `assets/` を使う流派もある。

重要なのは、ディレクトリ構造の見た目ではない。本文側で守るべきとは 2 つある。

(a) 補助ファイルへの案内を書く。SKILL.md 本文の末尾に、補助ファイルへの入口を一言ずつ書く。

## Additional resources

- 詳細な評価基準は `reference.md` を参照。
- 入出力例は `examples/sample.md` を参照。
- 検証スクリプトは `scripts/validate.sh` を実行。

copy
ポインタが書かれていない補助ファイルは、モデルから見れば存在しないのと同じだ。補助ファイルを置いたのに SKILL.md 本文に経路を書かないのは、段階的開示の最も初歩的な失敗である。

(b) 詳細はコピーせず、参照先を示す。HumanLayer は CLAUDE.md の文脈で同じ原則を提唱しているが、Skills の本文設計でも事情は変わらない。

`docs/knowledges/...` などに信頼できる仕様書や API リファレンスがあるなら、SKILL.md にコピペしない。`file:line` 参照を書く。コピペした内容は参照先と独立に古くなるが、ポインタなら参照先の更新に追従できる。

### 段階的開示の 3 つの失敗
![[Obsidian 2026-05-17 15.25.56.png]]
段階的開示とは、最初に読ませる情報を小さくし、詳しい情報は必要になったときだけ読ませる設計である。

Skill でいうと、最初に読む `SKILL.md` には最小限の手順だけを書く。長い説明、表、例、API 仕様は補助ファイルに分ける。そして、重い調査や評価は別コンテキストに逃がし、親会話には結論だけ戻す。

この設計が失敗する形は、次の 3 つに整理できる。

![[Pasted image 20260517152614.png]]
最初の 2 つは、情報をどこに置くか の失敗である。

1 つ目は、詳しい情報まで `SKILL.md` に詰め込む失敗。2 つ目は、詳しい情報を補助ファイルに分けたのに、そこへの道案内を書かない失敗である。どちらも、`SKILL.md` と補助ファイルの役割分担を間違えている。

3 つ目だけは、読ませた情報をどこに残すか の失敗である。

たとえば、判断材料として `ref-*` 系 Skill をいくつも発動するとする。各 Skill は単体では短くても、本文や参照内容が親会話に残り続ければ、合計量は増えていく。すると context 予算を圧迫し、後続タスクの判断にも古い情報が混ざる。

この場合は、補助ファイルに分けるだけでは足りない。読ませる場所そのものを分ける必要がある。

そこで使うのが `context: fork` である。重い参照を読む作業や、独立した評価を subagent に任せる。subagent は別コンテキストで作業し、親会話には短い結論だけを返す。これなら、大量の参照情報を親会話に残さずに済む。

![[Pasted image 20260517152620.png]]
つまり段階的開示には、2 つの設計がある。

どこに置くか — SKILL.md 本文に置くか、補助ファイルに降ろすか。

どこで読ませるか — 親話で読むか、forked subagent に読ませて結論だけ戻すか。

「SKILL.md は 500 行未満」という Tip は、このための経験則として理解するとよい。500 いう数字そのものが本質ではない。意味は「本文が肥大化していないか疑え」という警告であ。

100 行で十分な内容を、500 行まで膨らませ必要はない。逆に、頻繁に参照する短い表なら、SKILL.md 本文に置く方が合理的な場合もある。重要なのは、いま書こうとしている一行は、最初から読ませるべき情報か。それとも、必要になったときだけ読ませればよい情報か を毎回問い直すことだ。

### compaction で再付与される範囲
もう 1 つ、実務上の制約を押さえておく。一度呼れた Skill 本文は、同じセッションの後続ターン にも残る。ただし compaction を挟むと、再付与される範囲に上限がある。

compaction とは、履歴がコンテキストウィンドウを超えそうなときに、Claude Code が自動で要約・圧縮する挙動である。compaction 後に再付与される Skill 本文は、各 Skill の 先頭 5,000 token、合計 25,000 token までに限られる。

公式ドキュメント (Extend Claude with skills) より:

Auto-compaction carries invoked skills forward within a token budget. When the conversation is summarized to free context, Claude Code re-attaches the most recent invocation of each skill after the summary, keeping the first 5,000 tokens of each. Re-attached skills share a combined budget of 25,000 tokens. Claude Code fills this budget starting from the most recently invoked skill, so older skills can be dropped entirely after compaction if you have invoked many in one session.

なお、これは Claude Code 本体の仕様であり、2026 年 4 月時点 の挙動である。5,000 / 25,000 token という具体的な数値や「直近呼出から消費」というポリシーは、将来のバージョンで変更される可能性がある。設計判断は数値そのものに依存させず、「冒頭ほど残りやすく、古いほど落ちやすい」という方向性に紐付けておくのが安全である。

この仕様は、2 つの異なる「落ち方」を生む。

(1) 1 つの Skill 内での後半切り捨て。たとえば 10,000 token ある SKILL.md を呼んでいた場合、compaction 後に残るのは先頭 5,000 token だけで、後半 5,000 token は完全に消える。本文末尾に置いた重要ルールは、compaction を一度挟んだ瞬間に Claude の視界から消失する。

(2) Skill 単位での丸ごとドロップ。25,000 token の合計予算は、直近に呼ばれた Skill から順に消費 される。1 セッションで `/foo` → `/bar` → `/baz` … と多数の Skill を順番に呼んだ場合、compaction 後に再付与されるのは新しい順に予算が尽きるまでで、それより古い Skill は「先頭 5,000 token に切り詰められる」のではなく 本文ごと丸ごとドロップされ、再付与すらされない。会話の冒頭で発動した重要 Skill が、後続の周辺 Skill 群に予算を奪われて消える、という事故が起きうる。

この 2 つの制約から、SKILL.md の設計には次の規律が逆算できる。

最重要ルールは冒頭側に寄せる — 5,000 token の trim 境界より手前に確実に収める。

本文を長くしすぎない — 全文が 5,000 token を超えなければ (1) の trim 自体が起きない (述の「500 行未満」Tip もこの方向と整合する)

詳細な補助知識は別ファイルに降ろす — どせ trim されるなら最初から本文に積まず、必要時に Read させる。

重要 Skill は呼び直す前提で設計する — (2) で完全ドロップされた Skill は、ユーザー/orchestrator が再発動しない限り戻らない。「会話冒頭に一度呼べば最後まで効く」と仮定しない。

失敗しがちなのは

Read させる経路を作る。

設計時の問い
この章の規律を自分の Skill に当てはめるためのチェックリストを置いておく。

description だけを読んで、Claude は「いつぶか」を判断できるか。

SKILL.md 本文の最初の 30 行で「何をするか」「何を出すか」「重要な禁則」が分かるか。

補助ファイルを置いてい場合、本文にその到達経路が書かれているか。

本文に詰め込んでいる長い説明・大きな表・サンプルは、補助ファイルに降ろせないか。

compaction で後半が落ちても、最重要ルールは残るか。

開示した情報を「もう不要になったら手放す」設計にできているか (`context: fork` の活用を含む)。

書き終わったら、自分で SKILL.md を読み返して満足してはいけない。Claude に発動させて、Claude の挙動から逆算する。

書いたつもりの規律が効いているかは、自分の頭の中では確認できない。確認できるのは、モデルの出力だけである。

## Part 2. Skill を設計可能にする分類体系 (まさお提唱)
### 5. 最初の分岐 — 辞書型か、ワークフー型か
![[Pasted image 20260517152658.png]]
この章の核: Skill を作るときは、ず 副作用を持つか だけを見る。知識を読ませるだけなら辞書型。ファイル編集・コマンド実行・成果物生成まで任せるならワークフロー型である。

ここからは、本記事が提唱する規範体系に入る。

とはいえ、最初から細かく分類しようとしなくてよい。

最初に見るのは 1 点だけある。

その Skill は副作用を持つか。

副作用という言葉が少し硬ければ、「外から見て何か変わるか」と考えると分かりやすい。

たとえば、次のようなことをするなら副作用がある。

ファイルを作る

ファイルを編集する

コマンドを実行する

API を呼び出す

データベースを更する

チケットを作る

メールを送る

こうした変化を起こすなら、その Skill はワークフロー型として扱う。

逆に、Claude に規約・判断基準・業務知識を読ませるだけなら、辞書型として扱う。読んだ結果として Claude の判断は変わるが、ファイルや外部システムの状態は変わらない。

![[Pasted image 20260517152707.png]]
辞書型 Skill は、Claude の判断材料を増やすための Skill である。結果はファイルやチケットではなく、会話・設計判断・レビュー観点の質として現れる。

ワークフロー型 Skill は、観測可能な成果物を持つ Skill である。こちらは「完了しました」だけでは足りない。何のファイルがられたのか、何が変更されたのか、どの JSON が出たのかまで決める必要がある。

ここで分けているのは、Skill レイヤーの内部分類 である。

§2 で扱った「CLI / MCP / API のどれで実装するか」とは別の話だ。たとえば `run-deploy` が `gh` CLI を叩いてもよいし、`ref-api-conventions` が MCP schema を参照してもよい。実装層の選択とは独立に、Skill 自体の責務を「知識を読ませるもの」と「作業を進めるもの」に分ける。

この 2 種類は、できるだけ混ぜない。

たとえば「設計原則を説明しながらファイルも修正する」Skill は、だんだん責務が濁っていく。必要なら、設計原則を読む辞書型 Skill と、実際に修正するワークフロー型 Skill に分ける。ワークフロー側が辞書側を参すればよい。

### 辞書型を Skill にする意義 — docs/ ディレクトリと何が違うか
ここでよく出るツッコミに先回りしておく。

副作用がないなら、docs/ ディレクトリに markdown を置けばよいのでは?

たしかに、ファイルを書く / コマンドを実行する責務がない点では `ref-*` も docs/ も同じだ。違うのは、AI エージェント側から見たメモリの濃度 である。

![[Pasted image 20260517152736.png]]
`ref-*` スキルは 「CLAUDE.md ほど常時もたせたくないが、docs/ のように探されないと使われないのも困る」中間層 の置き場である。description で発動条件を契約しておけば、エージェントは関連する状況に入った瞬間に「この知が呼べる」と認識できる。docs/ にはこの仕組みがない。AI の頭の中には入っておらず、能動的に探しに行かないと存在すら気付かれない。

の常駐度の違いから、`ref-*` には docs/ にはない 2 つの活用が生まれる。

1. サブエージェントの「思考の道具箱」をプリロードできる

Subagent (Claude Code) や Agent SDK の Subagent は同じフロントマター仕様を共有しており、`skills:` フィールドにスキル名を列挙すると、起動時にそのスキル本文が 完全にサブエージェントのコンテキストに注入される (プリロード)。description で発動条件を契約してオンデマンドで呼ぶ通常のスキル発動とは別物で、起動時点で頭に入っている状態で動き始める。

---
name: api-developer
description: Implement API endpoints following team conventions
skills:
  - ref-api-conventions
  - ref-security-checklist
---

copy
「この専門家エージェントは `ref-api-conventions` と `ref-security-checklist` を頭に入れた状態で起動する」と宣言できるので、エージェントごとに思考の道具箱を組み立てられる。

サブエージェントは親会話らスキルを継承しないので、必要なものは明示的に列挙する。docs/ にはこの「エージェント単位で束ねて起動コンテキストへ注入する」規約がなく、ファイル命名で疑似的に揃えてもエージェント起動とは紐づかない。

2. メタハーネスでセッションログから育てられる

最近、過去のセッションログ・トレース (command logs / error messages / timeout behavior) を根拠にハーネスや Skill 自体を改善していく メタハーネス の議論が活発化している。

学術的には Stanford IRIS Lab の Meta-Harness 論文がこれを定式化しており、execution traces から failure modes を診断して harness (system prompts / tool definitions / completion checking / context management) を end-to-end で最適化する。

実装側では Hermes Agent (Nous Research) が経験から Skill を生成・改善するループを最も直接的に体現しており、近接領域として CLAUDE.md レベルで自己改善する claude-meta、単一ファイルに学びを蓄積する learnings.md パターンがある。

`ref-*` は「description で発動条件を契約し、本文に判断材料を持つ」構造なので、ログをると次が観測できる。

発動すべき状況だったのに呼ばれなかった → description (発動条件) を改善

呼ばれたが出力が不十分だった → 本文の断材料を追記

同じ指摘を別セッションで何度した → `ref-*` 側に gotchas として固定

このフィードバックを `ref-*` に書き戻せば、次回以降の全タスクの判断品質が底上げされる。docs/ は静的な置き場で、AI の判断ループとの接続が弱く、こうした自己改善ループが回りにくい。

どちらかではなく、役割が違う

docs/ が不要というわけではない。人間が直接読む静的文書 (アーキテクチャ概観、議事録、ADR、過去の設計判断記録) は docs/ が向く。

AI エージェントに「常時呼び出せる思考の道具」として渡したい知識は `ref-`。`CLAUDE.md` / `ref-` / docs/ はメモリ濃度の違う 3 層として併用する。

設計時の問い
その Skill が副作用を持つかを 1 文で説明できるか。

辞書型なのにファイルを書いてしまっていないか。書いているなら分割候補。

ワークフロー型なら、何を出力するか (ファイル / JSON / 状態変化) を明示できているか。

辞書型 / ワークフロー型は、あくまで最初の粗い網である。ここで完璧に類したいわけではない。目的は「混ぜると危ない責務」を早めに見つけることだ。

次章 では、この粗い分類を Purpose 軸 (`knowledge` / `produce` / `judge` / `pass-through`) でさらに細分する。ここでは粗く分ける。次章で細かく見る。

## 6. Skill を 4 の軸で記述する — Purpose / Trigger / Shape / Role
本記事では、Skill を次の 4 軸で記述する。

![[Pasted image 20260517152915.png]]
A・B・C は基礎軸 (常に値を持つ)。D は条件軸 (評価ループや委譲構造に参加する Skill だけが値を持つ)。

先に断っておく: 4 軸は完全には直交しない (Purpose=judge と Role=evaluator が相関、`wrap-*` は 4 軸では決まらない)。それでも採用する理由と限界は §6 末尾と §7「決定木の限界」で扱う。

この 4 軸はどう生まれたか
この 4 軸は、最初に分類表を作ってから Skill を当てはめたものではない。私自身が Skill を作り続ける中で、後から必要になって浮かび上がってきた便宜軸である。

最初に見えたのは Role 軸だった。特に大きかったのは、generator と evaluator を別 Skill に分けないと品質ループが狂うという気付きである。「作る側」と「見る側」を同じ Skill に入れると評価フェーズに生成時の文脈が残り、どうしても判定が甘くなる。

そこでまず、「品質ループや委譲構造の中で何役を担うのか」を表す条件軸として Role が立った。

ただし、すべての Skill が評価ループに参加するわけではない。Role を持たない Skill をどう説明するかが次の問題になった。

そこで残った要素を分解すると、「何を返すのか」(Purpose)、「誰が呼ぶのか」(Trigger)、「内部構造は単純か複合か」(Shape) という 3 つの問いに分かれた。

同時に、Skill がだんだん複合化していく傾向も見えてきた。たとえば動画作成のように、モーション技術、スクリプト、CLI 化を束ねる用途特化 Skill は、`wrap-` (派生) や `run-` (オーケストレーション) として重く育っていく。

こうした「アプリケーションレイヤー的な Skill 群」を 1 つの軸だけで扱うと破綻する。Purpose だけで見ると全部 `produce` に見える。Trigger だけで見ると全部 `user` に見える。だから、Purpose / Trigger / Shape を別々に問う必要があった。

つまり 4 軸は、最初から理論として設計した分類ではない。現実の Skill 群を見て、どこで責務が混ざり、どこで命名が崩れるのかを観察した結果、後から整理されたものである。だから完全な直交性は最初から目指していない (§6 末尾)。

Axis A: Purpose
![[Pasted image 20260517152941.png]]
`knowledge` は辞書型に対応する。`produce` / `judge` / `pass-through` は基本的にワークロー型である。

Axis B: Trigger
![[Pasted image 20260517152948.png]]
副作用の強 user Skill では、`user-invocable: true` だけでは不十だ。Claude に勝手に起動してほしくないなら `disable-model-invocation: true` を付ける。

ただし `user-invocable: false` の internal Skill (`assign-*` 系) には併記してはいけない — 両フラグが立つと Skill tool 経由が全部弾かれ、`/skill` 直叩きも閉じているため「誰も呼べない Skill」になる (§3 末尾の呼び出し制御マトリクス参照)。

Axis C: Shape
![[Pasted image 20260517152958.png]]
`atomic` は単純で保守しやすい。`orchestrated` は強力だが、設計を誤ると巨大化する。複雑な Skill を作る前に、複数の小さな Skill に分けられないかを見る。

Axis D: Role (条件軸)
Role はすべての Skill に必要な軸ではない。評価ループや複数エージェント構造に参加する Skill だけが値を持つ。

![[Pasted image 20260517153005.png]]
この 4 軸を埋められない Skill は、設計がまだ曖昧だ。特に Purpose が 2 つ以上に見える場合は、分割候補である。

### 4 軸で書いてみる — 両極の例
実例を 2 つ並べる。1 つは 4 軸が素直に決まる atomic な例、もう 1 つは 4 軸では決まりきらない限界の例である。両極を見ると、4 軸の射程と限界が一望できる。

例1: `ref-agent-essence` — atomic な knowledge 例
![[Obsidian 2026-05-17 15.30.09.png]]
LLM の構造的制約とハーネス設計原則を提供する辞書 Skill。Claude や他 Skill が「設計判断で詰まったときに参照する」ための知識源で、副作用は持たない。明示的に model-invocation を禁じてあり、ユーザーや親 Skill から ref として読まれることだけを想定する。

4 軸すべてが素直に決まる典型例である。

例2: `wrap-masao-ch-thumbnails` — 4 軸では決まらない限界例
この例を読む前に、依存関係を 1 行で先に置いておく。

ベース: `run-thumbnail` — YouTube / ブログ用のサムネイル画像を 1 枚単発で生成する汎用エンジン Skill (タイトル文字、レイアウト、色テーマなどをパラメータで受け取る)

wrap 側が上乗せするもの: `right-layout` (右寄せレイアウト) 固定 + 4 色テーマでの並列呼び出し

なぜ分けるのか: まさおCh というチャンネル固有のブランドプリセット (固定レイアウト・特定の色 4 種) を、汎用エンジン本体に混ぜたくない。エンジンは触らず、呼び出し側のラッパー Skill としてプリセットを外出しする

![[Pasted image 20260517153028.png]]
ここで 4 軸を埋めてみると気付く — `run-*` 系の単独 Skill と区別が付かない。`run-thumbnail` 自体も `produce / user / orchestrated / null` だし、他の `run-*` も同じ枠に入る。

つまり「まさおCh 固定プリセットの wrap」と「汎用 thumbnail エンジン」を分けているのは、frontmatter の `base: run-thumbnail` という 1 行 = 派生関係というメタデータである。これは Purpose でも Trigger でも Shape でも Role でもない別軸であり、4 軸の外側にある。§7 の prefix 決定木はこの二次分岐を持ち込んで初めて完結する。

言い換えると、`base:` という frontmatter キーは「4 軸では決まらない領域があることを Skill 側が明示するための逃げ道」として機能している。

### 4 軸の関係 — 「分類表」ではなく、設計レビュー用の問い
![[Pasted image 20260517153041.png]]
ここまで 4 軸を並べてきたが、これは数学的にきれいな分類表ではない。

Purpose / Trigger / Shape / Role は、完全には直交しない。重なる部分もあるし、運用中に値が変わるものもある。さらに `wrap-` と `run-` の違いのように、4 軸だけでは決めきれない領域もある。

それでも 4 軸を使うのは、Skill をレビューするときの問いを固定できるからである。

この Skill は何を返すのか。

誰が呼ぶのか。

中身は単純か、複合か。

評価ループや委譲構造の中で何役か。

この 4 問に分けると、Skill の責務が混ざっていないかを見やすくる。さらに、次章の prefix 決定木 (§7) への入力としてもそのまま使える。

ただし、限界はあ。主なズレは次の 5 つである。

![[Pasted image 20260517153048.png]]
要するに、4 軸は完全な分類理論ではない。設計レビュで同じ問いを毎回投げるための道具である。

別の軸セットも試した。3 軸にまとめる、派生関係を 5 軸目に昇格させる、といった案である。かし、どれも一部の Skill ではきれいに見える方で、別の Skill では説明しにくくなった。最的には、4 軸をレビュー用の便宜軸として使い、`wrap-*` のような例外は二次分岐で扱うのが一番破綻しにくかった。

## 7. 5 つの prefix — 名前は契約である
ここが本記事の中核である。

Skill 名の prefix を、感覚ではなく 4 軸から決める。prefix は次の 5 種類に限定する。

![[Pasted image 20260517153106.png]]
`assign-` は family 名であり、実際には `assign--generator`、`assign--evaluator`、`assign--contributor` のように role suffix を付ける。

決定木
![[Pasted image 20260517153115.png]]
![[Pasted image 20260517153120.png]]
この命名規則の目的は、美しさではない。

呼び出し側が契約を推測できることだ。

`ref-` で始まるなら、副作用のない参照知識だと分かる。
`run-` で始まるなら、ユーザーが直接叩く成果物生成 Skill だと分かる。
`assign-*-evaluator` なら、評価ループの採点側だと分かる。
`delegate-` なら、外部 LLM / agent に投げるだけで、成果物品質の保証は薄いと分かる。

名前はラベルではない。名前は契約である。

![[Pasted image 20260517153137.png]]
prefix を見た瞬間、Claude も人間も次の 事前条件 を置く。

`ref-` → 副作用ゼロ、Read-only で読み込む参照知識

`run-` → ユーザーが直接叩く独立ワークフロー、副作用は契約上明示

`wrap-` → 既存 Skill (`base:`) の派生、契約は base 側を継承する

`assign-*-evaluator` → fork で独立コンテキストの採点器、評価基準を触らない

`delegate-*` → 外部 LLM/agent への丸投げ、品質保証は薄い (出力を未信頼入力扱い)

これは合意ではなく prefix 呼び出し側に強制する事前条件 だ。命名を破と呼び出し側のコードと頭の両方が壊れる。命名規約とはそれだけ重い。

frontmatter の独自メタデータ — Claude Code は読まない、だから契約になる
次のフィールドは Claude Code の公式制御フィールドではない。本記事の設計体系で使う 任意メタデータ であり、Claude Code 本体は読まない。YAML として素通りするだけだ。

![[Pasted image 20260517153146.png]]
例:

---
name: assign-skill-review-evaluator
description: 「Skillレビュー評価」「SKILL.md採点」で発動。Skill設計を評価基準に照らしてJSONで採点する。
user-invocable: false
context: fork
agent: general-purpose
allowed-tools: Read Grep
pair: assign-skill-review-generator   # 独自メタデータ (公式ではない)
---

copy
なぜ独自メタデータを置くのか — 情報整理がまず先
正直に言えば、最初の動機は情報整理だ。

スキルはどんどん増える。10 個が 50 個になり、100 個になる。そのとき「`run-thumbnail` を派生元にしている `wrap-` は全部でいくつか」「`pair:` の片側だけ残って相方が消えた孤児はないか」「`ref-` のうち `kind:` が atomic なものはどれか」を、ある時点から目視で追えなくなる。

frontmatter に `base:` / `pair:` / `kind:` を書いておけば、grep / yq / 集計スクリプトで一瞬で答えが返る。棚卸しが機械化できる。

frontmatter は YAML なので拡張も効く。後から `owner:` `since:` `deprecated_in:` `replaces:` のようなタグを足してもコストはほぼゼロ。`base:` をエッジ、Skill 名をノードにすれば、派生の系譜を一枚のグラフにできる。`pair:` を見れば generator/evaluator のペア関係が図になる。Claude Code が読まなくても、自分の集計スクリプトは読める — これが第一の理由だ。

そして、Claude Code が読まないからこそ契約にもなる
情報整理のためのタグには、もう一段る。

Claude Code は `base:` も `pair:` も `kind:` も読まない。だから書いた値が嘘でも止まらない。`pair: assign-skill-review-generator` と書いた evaluator がの generator と組んでいても、エラーは出ない。

これは弱点ではなく自由度だ。値を読んで lint で検査する、依存グラフを描いて孤児を検出する、破った瞬間に CI で落とす — 強制力を書き手の側で組み立てられる。Claude Code が型として強制してこない代わりに、自分のツールで強制をかけられる。

破ったらどうなるか。たとえば `base: run-thumbnail` と書いた `wrap-*` が、実は thumbnail と関係ないことをしていたとする。Claude Code はエラーを出さない。けど呼び出し側の Claude は「これは `run-thumbnail` の派生だな」と前提を置いて読む。その前提のまま orchestrator が skill を選び、pipeline が stage を組む。間違った generator が走り、間違った評価が返ってくる。赤線は出ない。下流が静かに腐るだけ。

hooksなどで、で機械的に守らせるというアイデアもある。元々は情報整理のために置いたタグでも、lint と組み合わさって初めて契約として機能するというイメージだ

決定木の限界
この決定木は便利だが、万能ではない。次の 4 つの限界を明記しておく。

`wrap-` vs `run-` は 4 軸ではなく派生関係 (`base:`) で決まる二次分岐。

同じ Purpose/Trigger/Shape を持つラッパー Skill を `wrap-*` として隔離することで、責務の系譜が読み取れる。

代償として「4 軸から prefix が一意に決まる」主張は 95% 成立、5% は派生関係に依存する。

外部 LLM 委譲の prefix が Trigger で 2 系統に分かれる。

user 直叩きなら `delegate-` (例: `delegate-codex`)、内部から役割付きで呼ばれるなら `assign--{role}` (例: `assign-codex-generator`) と family が変わる。

運用中に Trigger が変わると名前変更が必要。

prefix 変更のコストは無視できない。orchestrator / CLAUDE.md / 他 Skill 本文の参照をすべて書き換える。最初の命名は決定木に従い、その後の変更は慎重に。

チーム導入時の抵抗。既存の `code-review-helper` を `assign-code-review-evaluator` に変えると「冗長」「機械的」と反発が出る。なぜ名前を契約にするか (自動探索の効率、責務の事前推測) を先に共有する。

完璧な類体系より、ほぼ機械的に決まり、限界を明示できる体系 が長期運用に耐える。

設計時の問
prefix が決定木と一致しているか。逆に prefix から 4 軸を復元できるか。

`wrap-*` を名乗るなら `base:` で派生元を示しているか。

`assign-*` を名乗るなら role suffix が付いているか。

Part 3. 読まれる Skill を書く
ここまでで分類と命名は片付いた。Part 3 は本文を「読まれる形」に書く作法。

## 8. Less is More — LLM が知っていることは書かない
![[Pasted image 20260517153203.png]]
Skill 本文に最も多い失敗は、書きすぎである。

LLM がすでに知っている一般知識を書いても、判断は改善しない。むしろ、重要なプロジェクト固有情報が埋もれる。

書くべきものは、Claude の通常の推論を「押し広げる」情報だけだ。

![[Pasted image 20260517153212.png]]
Skill は「親切な教材」ではない。エージェントの行動を変えるための設計文書であ。

前提: Claude は賢く、Claude Code は優れている
Less is More の根底にあるのは、「Claude は賢いモデル」「Claude Code は優れたハーネス」という前提に立つ ことだ。

例えば `gh pr create` の使い方や `git rebase` のオプションをわざわざ書き連ねるのは、Claude を賢くないものとして扱っているのと同じである。Claude が知っている可能性の高い情報を本文に並べるほど、本当に必要なプロジェクト固有情報が相対的に薄まる。書かないことで Skill の輪郭が立ち上がる。

例外: アンカリングが必要な領域
ただし、「賢いモデルでも一発で収束しない」領域はある。

高難易度なタスク

クリエイティブな出力 (デザイン、文章のトーン、コピーライティング)

「可愛い」「面白い」「賢い」のような 抽象度が高く広義 な語

抽象度の高い語は、ユーザーの脳内イメージと 100% 一致させるのが難しい。語が広義になるほど LLM の出力は「無難な 80 点」に収束する。ここでだけ、LLM がすでに知っていることでも 意図的にバイアスをかけ、アンカリングを置く 価値が出る。Claude が「可愛い」を知らないのではなく、ユーザーが想定する「可愛い」の一点に寄せるための補正である。

これはあくまで例外であり、原則ではない。根本の哲学は「Claude が賢く、ハーネスが優れている」前提に立つこと
そこから逸脱する箇所だけ、明示的に補強する。逆順に始めると、Skill はすぐに一般教養の写経になる。

悪い本文
この Skill は GitHub の Pull Request を作成するための Skill です。

GitHub CLI (`gh`) は GitHub をコマンドラインから操作するための公式ツールで、`gh pr create` で PR を作成できます。主なオプションは次のとおりです。

- `--title <string>` — PR のタイトルを指定
- `--body <string>` — PR の本文を指定
- `--base <branch>` — マージ先のブランチ (通常は `main` または `master`)
- `--draft` — Draft PR として作成

事前に `gh auth login` で認証されている必要があります。また、現在のブランチが remote に push されていない場合は `git push -u origin <branch>` を実行してから `gh pr create` を呼んでください...

copy
`gh` の使い方は Claude が知っているこれは Skill ではなく `gh --help` の写経である。

良い本文
このリポジトリで PR を作るときは、のワークフローで行う。

1. **ブランチ名を検証** — `feat/`, `fix/`, `chore/` のいずれかで始まること。違えば `git branch -m` でリネームしてから進める。
2. **CHANGELOG を確認** — `feat/` `fix/` の場合は `CHANGELOG.md` の `## Unreleased` 節にエントリが追加されているか確認。なければ追記してコミッを積む (社内ルール: リリースノート自動生成入力になるため必須)。
3. **タイトルは Conventional Commits 形式** — `<type>(<scope>): <subject>` 。`type` は branch prefix と一致させる。
4. **Body には Linear チケットリンクを冒頭に置く** — `Closes ENG-1234` の行が無いと、自動 close 連携が走らない。
5. **draft で作る** — `gh pr create --draft` 。CI が通って自分で動作確認したあと `gh pr ready` で外す。レビュアーの通知ノイズを減らすための社内合意。
6. **レビュアー指定** — `CODEOWNERS` で自動付与されるが、UI 変更を含む場合は `@design-review` を手で追加する。

copy
悪い本文は「`gh` とは何かを語っているが、良い本文は `gh` が使えることを前提に、このリポジトリでだけ通用する規約ワークフロー を語っている。Skill に必要なの後者である。

Why-driven — 命令には理由を添える
Less is More が「何を書くか」を絞る原則だとすれば、Why-driven は「どう書くか」を決める原則だ。残った運用知識を本文に落とすとき、ほぼ必ず迷うのが「どこまで強く書くか」である。結論は単純で、強く書くより、理由を書く 方が効く。

LLM は強調ではなく妥当性で判断する
`ALWAYS` `NEVER` のような全大文字命令は、人間には強く見える。だが LLM はその逆で、命令の 強調 でなく 妥当性 で従うかを決める。

理由のない令は、新しい文脈に当たった瞬間に上書きされる ──「`ALWAYS validate input` と書いてあるが、ここはテストコードだから skip して良いのでは ?」と。理由が書いてあれば、LLM は 同じ判断軸を新しい状況にも当てはめる ことができる。これが Why-driven の本体だ。

Anthropic 公式メタスキル `skill-creator` も同じ立場をとる ── 「`ALWAYS` / `NEVER` を全大文字で書きそうになったら、それは黄信号。可能なら理由を添えて書き直せ」と明言している。

悪い書き方
**ALWAYS** validate input before passing to API.
**NEVER** call the deploy endpoint without confirmation.

copy
良い書き方
API 呼び出し前に input を validate する。
失敗した validation は API 側でリトライできず、上流で 400 を返すと Orchestrator が駄な再実行を走らせる。手前で止めれば、ループの予算を節約できる。

Deploy endpoint はユーザ確認なしで呼ばない。
本番反映は副作用が不可逆で、巻き戻しに人間の判断が要る。`allowed-tools` だけでは Edit/Write 系を止め切れないので、明示的な confirmation step を本文で要求する。

copy
語気は弱くなった (「絶対」「決して」が消えた) のに、従う確率はむしろ上がる。LLM が「なぜのルールがあるのか」を理解しているからだ

もう一つの技法 — 条件で囲む `<important if="...">`
理由を添えるのと同じ発想で、もう一つの書き方がある。適用条件を明示する ことだ。CLAUDE.md や SKILL.md で、特定の状況だけ効かせたいルルを `<important if="...">` で囲む (HumanLayer の Stop Claude from ignoring your CLAUDE.md で紹介され、定着しつつあるパターン)。

<important if="you are writing or modifying tests">
- Use `createTestApp()` helper for integration tests.
- Mock database with `dbMock` from `packages/db/test`.
- Snapshot ファイルは `__snapshots__/` 配下のみ。手動編集は禁止 (CI で再生成される)。
</important>

<important if="you are modifying .claude/settings.json (hooks or permissions)">
- フックは 6 種。該当ライフサイクルの `hooks` 配列にエントリを追加する。
- permissions の `allow` は `.claude/**` への Edit/Write/Read に限定。外部パスへ広げる前に影響を確認する。
</important>

copy
これは強調 (`ALWAYS`) でも理由でもなく、スコープ で重みを与える書き方だ。条件が明示されているから、関係ないタスクのときは LLM が安全に無視でき、関係あるタスクのときは強く効く。`ALWAYS` を叫ばなくても、必要な場面で必要な強度が出る。

うまく使うコツは 3 つ。

何でも囲まない ── プロジェクト識別、ディレクトリ構造、tech stack のような全タスクで関係する報は外に置く。`<important>` だらけの CLAUDE.md は局すべてを「重要」と言っているのと同じになる。

条件は具体的に ── `if="you are writing code"` のような広すぎる条件はほぼ全タスクに当たり、囲む意味がなくなる。「テストを書く / 修正する」「`.claude/settings.json` を変更する」「PR を作る」のように、特定アクティビティ で絞る。

Why-driven と排他ではない ── 条件で いつ を絞り、本文で なぜ を説明する。両方を組み合わせれば、命令を強めずにルールを効かせられる。

結果として、ルールの強さを表現する手段は 3 つに整理される ── 強調する / 理由を書く / 条件で囲む。最初の 1 つはほぼ使わず、後ろ 2 つを組み合わせる。これが本記事を通じて推奨する書き方だ。

### Less is More と Why-driven の役割分担
![[Obsidian 2026-05-17 15.32.20.png]]
順序も重要だ。先に Why-driven から始めると、一般知識まで「理由つきで」太らせてしまうLess is More で削ってから、残ったものに Why-driven で肉付けする。

例外: 理由なしの大文字命令を残してよい場合
運用上「絶対に譲らない不変件」で、かつ理由を書くまでもなく自明な場合に限り、理由なしの大文字命令を残してよい。評価器は評価基準を編集しない」のような 安全に関わる絶対条件 がそれに当たる。それ以外で `ALWAYS` / `NEVER` を見たら、設計が曖昧になっているサインだ。

## 9. Gotchas — 失敗から育つ運用識
Less is More と言っても、例外的に育て続ける価値があるセクションがある。それが Gotchas だ。

Gotchas は、LLM が実際に踏んだ落とし穴の記録である。一般論ではなく、運用から出た失敗を書く。

良い Gotcha は 1 行 + 短い理由 で書く。読み手は LLM だから、文脈は推論で埋まる。複雑に書きすぎても、Skill の他の重要箇所が token 予算から落ちる。

これは複数の実践者が収束した結論でもある。Peter Steinberger は CLAUDE.md について「concise と明記しないとモデルは段落を返してくる」と注意し、CLI 系の指示は 1 行で十分 (`logs: axiom or vercel cli`) と書く。

HumanLayer は Writing a good CLAUDE.md で 60 行目安・上限 300 行 を提示し、長くなるほど Claude が各セクションを optional 扱いし始めると指摘する。

Anthropic 公式メタスキル `skill-creator` は Gotchas を最も価値のある節の 1 つと位置付ける一方、"stale gotchas"  古くなった落とし穴は Claude を 存在しない問題に追わせる 害になる、とも明示している。1 件あたりが短いほど、書く・読む・捨てるすべてが軽くなる。

良い Gotcha の条件:

見出しでトラップの核を渡す ── タイトルだけで「何が罠か」が分かる。

本文 1〜2 行で why と回避 ── why が分かれば、LLM は新しい状況にも応用できる (Why-driven の系譜)。

具体的・検証可能に書く ── 「正しく扱うのような曖昧表現は禁止。コマンド名・フラグ名・閾値・ファイルパスで書く (Anthropic 公式 Best practices for Claude Code も "concrete, verifiable rules" を要求する)。

賞味期限を意識する ── ライブリの更新や API 変更で前提が崩れたら削る。残コストは tokens、削るコストはほぼゼロ。stale Gotcha は無いより悪い。

例:

## Gotchas

- **`allowed-tools` は allow-list、deny ではない** — `Read Grep` だけ書いても、Edit/Write が permissions で許可なら呼べる。書き込み禁止は permission の deny rule で行う
- **compaction 後の Skill listing は圧縮される** — 各 Skill 先頭 5,000 token / 合計 25,000 token に落ちる。発動条件・禁止・output contract は SKILL.md 冒頭 30 行に集約し、詳細は補助ファイルへ。
- **`pair:` 書き忘れは lint で防ぐ** — Claude Code が処理しない任意 frontmatter なので、忘れても起動には影響せず気づきにくい。CI で必須化し、人間の注意力に頼らない。

copy
Gotchas は最初から完成しない。運用しながら増える。

ただし、Gotchas に書くだけで満足してはいけない。同じ失敗が再発するほど、より重い決定論システムへ寄せていく ── これが Gotchas 運用の本筋だ。頻度はトリガーであって、ゴールではない。ゴールは「人間 LLM の注意力に依存する弱い防御」を「コードで強制される強い防御」に置き換えることであ。

昇格の階段 — 軽い決定論から重い決定論
![[Pasted image 20260517153330.png]]
階段を 1 つ上がるたびに、書くコストは増えるが、再発確率はゼロに近づく。ライブラ化までいけば、その失敗は自分のリポジトリけでなく将来の自分や他人のリポジトリでも起きなくなる。

昇格の判断基準
頻度だけで昇格を決めない。次の 3 つを総合的に見る。

再発頻度  月に何度もハマるなら、Gotchas はもう負け。1 つ上に上げる。

ブラスト半径 失敗時の被害大きいほど (本番事故、データ破壊、CI 全停止)、低頻度でも上の段に飛ばす。

検出可能性 frontmatter フィールド漏れや特定文字列の有無のよに、決定論で書ける ものは Gotchas に置かず即 lint へ。LLM の注意力で確率的に防ぐより、ルールで 100% 防ぐ方が常に安い。

LLM の注意力に依存する防御は構造的に弱い。Gotcha のまま据え置く判断は「決定論で書けない」「頻度が低い」「被害が小さい」が 3 つ揃ったときだけだ。

## 10. 動的コンテキスト注入 — `!` パターンと外部 LLM
Claude Code Skills には、`!` 構文による動的コンテキスト注入がある。主な用途は決定論的な CLI 出力 (`git` / `gh` / `jq` / `rg` など) を Skill 本文に焼き込むこと だ。Claude が Bash tool を呼ぶのとは違って、Skill がレンダリングされる前にコマンドが実行され、stdout が本文に埋め込まれる。Claude はコマンド自体ではなく、展開済みの結果を見る

主用途 1: Git / GitHub の状態を Skill に流し込む
![[Pasted image 20260517153351.png]]
PR レビュー、リリース確認、デプロイ前チェックは、まず「今どうなっているか」の事実から始まる。`!` 注入はこの事実取得を Skill 本文に埋め込む。

## Pull request context

- PR diff: !`gh pr diff`
- PR comments: !`gh pr view --comments`
- Changed files: !`gh pr diff --name-only`

## Working tree

- Modified files: !`git status --short`
- Last 5 commits: !`git log --oneline -n 5`

copy
これらは 決定論的 で、外部 LLM の判断を含まない。Claude は確定した事実の上で推論する。

主用途 2: 構造化データを `jq` で整形して埋める
ローカルの JSON / 設定ファイルから必要部分だけ抽出して埋める使い方も多い。

## Active deployments

- Environments: !`jq -r '.environments | keys | join(", ")' deploy.json`
- Last deploy SHA: !`jq -r '.last_deploy.sha' deploy.json`

copy
複数行コマンドなら次の形を使う。

```!
node --version
npm --version
git status --short
```

copy
応用: 外部 LLM CLI を呼ぶ — 副次的な使い方
`!` 注入には外部 LLM CLI (`codex` / `gemini` / `claude -p` 等) を呼ぶこともできる。ただしこれは 副次的な使い方 であり、上記 2 つの主用途とは扱いが異なる。

## 別モデル視点のレビュー (副次的)

!`codex exec "この差分の設計上の懸念を3点に絞って指摘してください"`

copy
外部 LLM の出力は 未信頼入力 として扱う。

その出力を評価基準に昇格させない。

長期記憶や `ref-*` にそのまま貼らない。

セキュリティや権限判断の根拠にしない。

出所を明示し、一時的な参考意見として扱う。

決定論的 CLI と外部 LLM CLI を 同じ `!` 構文 で混ぜると、Skill 本文が「事実 + 意見」の混合になる。読み手 (Claude 自身) が両者を見分けられないと、意見を事実として扱う事故が起きる。本文中で 見出しレベルで分離 する (例: 「## Facts」と「## Other-LLM views」)、あるいは外部 LLM 呼び出しは別の `delegate-*` Skill に切り出すのが安全だ。

派生形: forked Claude を仲介に立てる
外部 LLM CLI の出力をそのまま親エージェントの context に流し込みたくないとき、fork した Claude を 1 段噛ませて仲介させる 使い方がある。

親エージェント
  └─ Subagent (fork した Claude)
        └─ !`codex exec "..."`  ← 外部 LLM CLI
        └─ 出力を読んで要約・抽出・評価
        └─ 構造化済みの結果だけを親に return

copy
外部 LLM の生出力は fork 側の context で消費され、親には fork 側 Claude が責任を持って整形した最終結果だけ が返る。「未信頼入力を信頼境界の外で処理してから、信頼できる形で持ち込む」というパターンで、本文中の `!` 直接埋め込みより安全な選択肢になる。

Part 4. 評価駆動で Skill を運用する
設計と本文は片付いた。残りは「動かして、本当に良いと判定する」工程。Anthropic の harness (エージェントを動かす外側のループ・足場) 設計記事の原則 (生成と評価の分離) を Skill 構造に落とす。

## 11. 「できました」を信用しない — generator と evaluator を分ける
ワークフロー型 Skill の最大の罠は、Claude の自己申告を完了判定にしてしまうことだ。

「完了しました」
「問題ありません」
「高品質に仕上げました」

これらは output ではない。

Anthropic の harness 設計記事でも、生成する agent と評価する agent を分けることの重要性が述べられている。自分が作った成果物を自分で評価させると、LLM は甘くなりやすい。

これは LLM-as-a-judge における sycophancy (自己迎合) と呼ばれる現象で、モデルが自分自身や対話相手の出力を過剰に肯定する傾向として報告されている。だから、作る側と見る側を分離する。

本記事の体系では、これを Skill 構造として表現する。

Generator と Evaluator が pair で揃っていれば、合否判定の再実行制御は専用 Skill を毎回作る必要はなく、汎用の指揮役に任せられる。役割分離さえ守られていれば、上位の指揮構造は差し替え可能で良い。

Evaluator は同じコンテキストで動かさない。`context: fork` や Subagent を使い、別コンテキストで成果物を初見として読む。

Evaluator の出力は感想文ではなく構造化する。スコアと合否判定を機械可読にしておけば、再実行を司る指揮役が機械的に判定できる。

スキーマ設計と Goodhart の罠 (agent が成果物ではなく rubric を書き換えに行く失敗) の防御は別レイヤーの話なので、最後の節で宿題として整理する。

自己申告は debug できない。評価器は debug できる。 この差が長期運用を分けると思っている
