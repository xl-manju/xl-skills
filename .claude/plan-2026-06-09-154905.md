# 郵便番号取得を 日本郵便 addresszip API へ一本化する移行計画（codexレビュー反映版）

## ゴール
company-master プラグインの郵便番号取得を、**日本郵便「郵便番号・デジタルアドレスAPI」(addresszip V2) のみ**に一本化する。KEN_ALL + jigyosyo 逆引きとその支援機構（DL/キャッシュ/手動取り込み/縮退）を撤去する。gBizINFO は会社同定（法人番号・正式名称・住所）用なので存置。出力先は Notion（会社情報取得_DB）据え置き。実行は **ローカル Claude Code スキル起動**（「〇〇社の情報/郵便番号を取得して」等の自然言語で発火）。IP 認証はローカル機の送信元 IP を日本郵便に登録して満たす。

## 設計原則（最重要）
**データソースの interface を保ったまま engine だけ差し替える「配管の付け替え」**。
`enrich_company.postal_from_address()` が依存する戻り値インターフェース
`{value, certainty, remark_key, source_url, attempts}` を新実装でも厳守する。確度ラベル値域は不変（`公的データ取得` / `未確定(要確認)`）。

> **codexレビュー反映**: 「ken_all」という文字列が validate（確度ゲート）と enrich（備考分岐）に暗黙の結合点として散在しており、文字列一致で繋がっているため改名/差し替えで静かに壊れる。よって `grep -ri ken_all plugins/company-master` が **0 件**を移行完了の機械条件とする。

## 現状（確認済み）
- 郵便番号: `enrich_company.postal_from_address()` → `ken_all.lookup_postal()`（KEN_ALL 最長一致 → jigyosyo 第二索引）。
- 確度: 一意確定のみ `公的データ取得`、非確定は空欄+`未確定(要確認)`+備考（誤値を入れない非対称コスト原則）。
- origin 契約: `validate_company_master.py` の `ORIGIN_CERTAINTY_CAP` / `FIELD_ALLOWED_ORIGINS` / **`SOURCE_URL_REQUIRED_ORIGINS`** / **validate_row 内の「ken_all は source_url 任意（weak provenance 許容）」分岐**が `postal_code`×`ken_all` を機械強制。
- 認証 SSOT: `notion_config.py`（Notion / gBizINFO トークンを Keychain+env で解決）。
- addresszip / japanpost-da の既存参照は company-master 配下に **0 件**（完全新規組み込み）。

## lookup_postal 互換契約（B2 対策・新実装が満たすべき仕様）
新 `postal_api.lookup_postal(normalized_address, company_name="")` は次を厳守する:
- 戻り値キー: `value`(NNN-NNNN or "") / `certainty` / `remark_key` / `source_url` / `attempts`。
- `attempts[]` の各要素: `{source, pattern, result, reject_reason}`。
  - `source` は新 origin 名に統一（後述 `japanpost`）。
  - 成功=`result:"hit"` / 一意不能=`"miss"` / 取得失敗=`"error"`（`reject_reason` に 401/403=認証, 5xx/timeout=通信, の種別語を含める）。
- **enrich 側の remark 分岐を同時改修**: 現行の `source=="ken_all" and result=="error"` ハードコードを撤去し、`result=="error"` の `reject_reason` 種別で `postal_api_unauthorized` / `postal_api_unavailable` を、`result=="miss"` で `postal_code`(一意不能) を選ぶ対応表に置換する。

## 主要な設計判断
1. **新スクリプト `scripts/postal_api.py`** を新設し上記互換 API を提供。内部: `get_token()`（client_credentials + `x-forwarded-for`、**expires_in を尊重したプロセス内メモ化**＝M1対策） / `search_zip()`（POST /api/v2/addresszip, Bearer） / `pick_best()`（level+候補で確定判定・純関数） / `address_to_query()`（住所→検索クエリ・純関数）。`lookup_postal(..., _search_fn=None)` の**注入口**を設け、CI ではネット非依存にする（M2対策）。
2. **origin enum `ken_all`→`japanpost` に改名**。波及（全件改名スコープ）: `enrich_company.ORIGIN_KEN_ALL`、`validate_company_master` の **`ORIGIN_CERTAINTY_CAP` / `FIELD_ALLOWED_ORIGINS` / `SOURCE_URL_REQUIRED_ORIGINS` / weak-provenance 許容分岐**（B1対策）、`confirm-url-template.md` 由来表記、`data-sources.md`、`test_provenance_contract.py` 他テスト。`japanpost` も **source_url 任意（weak provenance）**を維持。
3. **住所→検索クエリ（M4対策）**: 第一段は `normalize.py` から `pref_name/city_name/town_name` を抽出した**構造化検索**、不足/未ヒット時のみ番地除去 freeword へフォールバックの2段。freeword 単独の取りこぼし/誤一致を避ける。
4. **確度マッピング**: addresszip の `level`(1/2/3) と `pick_best` の一意性で判定。一意確定（level=3 単一 or 候補 zip 収束）→ `公的データ取得`。非確定 → 空欄+`未確定(要確認)`+備考。誤値を入れない原則を厳守。
5. **認証**: `notion_config.py` に `get_japanpost_credentials()`（Keychain `japanpost-da-api`/`client_id`,`secret_key`）と `get_japanpost_egress_ip()`（env `COMPANY_MASTER_EGRESS_IP` 優先）を追加。未設定は明示エラー。
6. **検証 URL**: 定数名を `KEN_ALL_VERIFY_URL`→**`JAPANPOST_VERIFY_URL`** へ改名（m1対策）。weak provenance（per-value URL なし）は維持。

## 日本郵便APIキー セットアップ手順の記述（ユーザー要望）
- 新規 `references/japanpost-api-setup.md` を正本として作成。内容: ① for Biz 登録（ゆうID→組織→システム登録）→ ② 送信元IP（最大10件）登録 → ③ client_id/secret_key 取得（secret は初回のみ表示）→ ④ **Keychain 保存**:
  - `security add-generic-password -U -s japanpost-da-api -a client_id -w '値'`
  - `security add-generic-password -U -s japanpost-da-api -a secret_key -w`（**-w を空にして対話入力**＝平文を履歴/ログに残さない）
  - 確認: `security find-generic-password -s japanpost-da-api -a client_id -w`
  - 注意: 貼付時の U+2011 等不可視ハイフン・空白混入、回線が固定IPでない場合の再登録。
- `skills/run-company-master-build/SKILL.md` / `run-company-master-backfill/SKILL.md` の**セットアップ節からこの手順へリンク**。
- `doctor` がキー/IP 未設定時にこの手順を案内（WARN）。

## リスク・留意
- IP 認証はローカル回線のグローバル IP 依存。固定 IP でないと変動 → doctor `--probe`(egress vs 登録IP) + SKILL 運用注意 + ズレ時 `postal_api_unauthorized`。
- addresszip 逆引きは曖昧候補が出るため構造化検索優先 + `pick_best` で誤値抑制（誤値を入れない原則維持）。
- elegant-review 済みの確度契約・hook fail-closed・書き込みゲートを壊さない（確度値域不変・validate 契約維持）。
