# 作業日報生成スキル ヒアリングシート

## 0. 一行サマリ

その日の作業を口頭・チャット入力で投げると、**案件単位で縦に束ねた構造化テキスト日報**（Slack 直貼り用 .txt）を企業ごとに出力する。各案件には[ステータス]・本日の対応・残課題・ご相談・期限と完了確率(%)が紐付き、受け取り手は1案件ずつ縦読みで全把握できる。Markdown 非使用。会社ごとのナレッジは JSON で蓄積され自己進化。

## 1. 真の課題（Why）

表層の要望: 「作業日報を毎日書くのが面倒」

深掘り後の真の課題:
1. **思い出しコスト**: その日何をやったかの想起・整理に時間がかかる
2. **整形コスト**: 毎回フォーマット・体裁を整える手間
3. **翻訳コスト**: 自分の作業ログ→相手に伝わる粒度・表現への変換
4. **配置ミスコスト**: 企業ごとの保存先・ファイル名のミス
5. **学習されない**: 過去にうまく伝わった日報のパターンが個人の頭にしか残らず、毎回ゼロから書いている

→ それで何が浮く?: 1日あたり約15-30分。さらに「相手にちゃんと伝わる」品質が安定する。

## 2. 出力先（Where）

- ベースディレクトリ: `05_Project/00_業務委託/00_作業日報/`
- 企業別ディレクトリ: 配下に企業ごとのフォルダ（現状: `01_XLOCAL/`, `02_ジョウホウソース/`、随時追加）
- 日報ファイル名: `YYYY-MM-DD_<AI生成の概要タイトル>.txt`
- 形式: **Slack 貼付前提のプレーンテキスト+構造化記号**（Markdown 非使用）
- 「Markdown版・チャット版」の二重出力は廃止。本体一本で Slack に貼れる
- **ナレッジは「ファイル名で全管理」**。サブディレクトリを切らず、企業ディレクトリ直下に JSON で平置き

```
05_Project/00_業務委託/00_作業日報/
├── 01_XLOCAL/
│   ├── 2026-04-30_契約書テンプレ整備.txt
│   ├── _knowledge_XLOCAL_tone-style.json
│   ├── _knowledge_XLOCAL_glossary.json
│   ├── _knowledge_XLOCAL_samples_2026-04.json
│   └── _knowledge_XLOCAL_workflow.json
├── 02_ジョウホウソース/
│   ├── 2026-04-30_xxx.txt
│   ├── _knowledge_ジョウホウソース_tone-style.json
│   └── _knowledge_ジョウホウソース_glossary.json
└── <随時追加される企業>/
```

### ナレッジファイル命名規則（ファイル名駆動管理）

`_knowledge_<企業名>_<トピック>[_<分割キー>].json`

- プレフィックス `_knowledge_`: 日報本体と区別、ls で先頭にソート
- `<企業名>`: ディレクトリ名と一致（冗長だが grep・横断検索が容易になる重要冗長性）
- `<トピック>`: 責務単位。1ファイル=1責務
  - `tone-style`: 敬語レベル・文体・粒度
  - `glossary`: 用語・略語・固有名詞辞書
  - `workflow`: 業務フロー・タスク種別
  - `samples`: 採用された日報サンプル（評価済）
  - `feedback`: 受け取り手からの指摘・要望ログ
  - `personas`: 受け取り手のプロフィール・好み
- `<分割キー>`: 500行超え対策。`_2026-04`（年月）や `_001`（連番）で分割

### ナレッジファイルサイズ制約

- **1ファイル500行を超えない**。超えそうになったら自動で分割キーを付けて新ファイル化
- 分割時の規則: `samples` は年月、`glossary` は連番、`feedback` は年月で分割
- スキル本体に「サイズチェック→自動ローテーション」ロジックを実装する

## 3. 情報源（Where from）

- 主入力: **その場で口頭・チャット入力**（ユーザーがスキルとの対話で1日の作業を語る）
- 補助参照（任意・将来拡張）: Obsidian daily ノート / git log / Slack
- AI は対話で「今日まず何をやった?」「次に?」「ハマった所は?」と引き出す

## 4. 共有相手と中身（Who & What）

- 受け取り手: 業務委託先（XLOCAL、ジョウホウソース、その他随時追加）
- 共有手段: **ローカル保存のみ・手動コピペで送る**（自動送信なし）
- 同時に「チャット貼付用の短め要約」も別ファイルで出力する

伝えるべき主要項目:
1. 今日やったこと（成果・進捗）
2. 課題・相談事項
3. 明日以降の予定
4. 稼働時間・工数

## 5. ナレッジ資産（Knowledge）

- 現状: 過去サンプルはまだ揃っていない
- 方針: **これから書く日報そのものを、会社ごと・トピックごとに JSON ファイルへ蓄積**する自己進化型
- 設計の背骨:
  1. **ファイル名で完全管理**（ディレクトリのネスト禁止）。`_knowledge_<企業>_<トピック>[_<分割>].json`
  2. **責務ごとに1ファイル**（tone-style / glossary / workflow / samples / feedback / personas）
  3. **1ファイル500行上限**。超えたら自動分割
  4. **JSON は文脈リッチ構造**。AI が検索・参照しやすいメタデータを必須化

### JSON スキーマ（共通）

```json
{
  "company": "XLOCAL",
  "topic": "tone-style",
  "split_key": null,
  "version": "1.3",
  "created_at": "2026-04-15",
  "updated_at": "2026-04-30",
  "summary": "業務委託先 XLOCAL 担当者が好む文体・粒度のルール集",
  "applies_when": "XLOCAL 向けの日報・チャット要約を生成するとき",
  "keywords": ["敬体", "ですます", "粒度", "簡潔"],
  "related_files": ["_knowledge_XLOCAL_glossary.json", "_knowledge_XLOCAL_personas.json"],
  "entries": [
    {
      "id": "tone-001",
      "title": "敬体で書く",
      "context": "受け取り手は丁寧語を好む。タメ口・体言止めは避けたい",
      "rule": "全文ですます調。動詞は「〜しました」「〜します」",
      "examples_good": ["契約書テンプレートの整備を完了しました"],
      "examples_bad": ["契約書テンプレ整備、完了"],
      "evidence": "2026-04-15 Meet で坂本さんから『日報は丁寧めが嬉しい』と発言",
      "evidence_source": "minutes - 2026-04-15.md",
      "tags": ["tone", "敬体"],
      "weight": 0.9
    }
  ]
}
```

### スキーマ意図（AI が文脈で検索・取得できる仕掛け）

| フィールド | 役割 |
|-----------|------|
| `summary` / `applies_when` | AI が「いつ参照すべきか」を即判定できる |
| `keywords` | 部分一致・タグ検索の入口 |
| `related_files` | 関連ナレッジへの明示リンク。AI が芋づるで読める |
| `entries[].context` | そのルールが効く前提条件。文脈マッチ用 |
| `entries[].evidence` + `evidence_source` | 根拠の追跡可能性。ハルシネーション抑止 |
| `entries[].weight` | ルールの重要度（0〜1）。競合時の優先順位判定 |
| `entries[].tags` | 横断検索・複合フィルタ |

### トピック別 JSON の責務（ファイル分割の指針）

| トピック | 責務 | 主な entries フィールド |
|---------|------|----------------------|
| `tone-style` | 文体・敬語レベル・粒度ルール | rule, examples_good, examples_bad |
| `glossary` | 社内用語・略語・固有名詞 | term, reading, definition, aliases |
| `workflow` | 業務フロー・タスク分類 | task_type, typical_duration, deliverables |
| `samples` | 採用された過去日報の本文 | date, title, body, why_good |
| `feedback` | 受け取り手からの指摘ログ | date, issue, fix_applied |
| `personas` | 受け取り手プロフィール | name, role, preferences, dislikes |

### 自己進化フロー

1. 日報生成時: 対象企業の `_knowledge_<企業>_*.json` を全件読み込み → entries を統合してプロンプトコンテキストに注入
2. 日報承認時: ユーザーが「良かった」と判定 → `samples` トピックへ自動 append
3. 用語検出時: 新しい用語・略語が出たら `glossary` への追記候補を提示
4. フィードバック受領時: 受け取り手の指摘をユーザーがコピペ → AI が `feedback` トピックに構造化追記
5. サイズチェック: append 前に行数を測り、500行超なら新分割キーで新ファイル作成

## 6. UX 仕様（確定済み）

| 観点 | 決定 |
|-----|------|
| 企業選択 | `00_作業日報/` 配下を自動 ls して選択肢を提示。`_knowledge` で始まるものは除外 |
| 新規企業対応 | 「新しい企業を追加」選択肢を末尾に追加。選ぶとディレクトリ作成 |
| 概要タイトル | AI が作業内容から10-20字の候補を提案 → 人間が承認/微調整 |
| 稼働時間 | 人間がチャットで申告（例: 「今日4時間」）。AI は推論しない |
| 体裁 | **Slack 貼付前提のプレーンテキスト**。Markdown 非使用。記号で構造化 |
| 共有手段 | メインは **Slack 共有**。ファイル開いて全選択コピー→Slack に貼って送信 |

### 日報フォーマット仕様（Markdown 非使用・Slack 直貼り・抽象番号束ね構造）

**設計思想**:
1. **項目（番号）単位で縦束ね** … 「案件」のような業態限定語は使わず、`①②③` の番号だけで抽象化。中身（タスク／調査／不具合／成果物 何でも）に拘束されない
2. **二段構造でスキャン性と詳細性を両立** … 上部に「ヘッドライン」（番号+1行+ステータス+%）、下部に各番号の詳細展開。受け取り手は上だけで把握→気になる番号だけ下に降りる
3. **ステータスごとに必要要素を可変化** … 完了は最小、進行中・未着手・ブロック中は厚めに。冗長を排除
4. **意思決定優先順で並べる** … 物理順ではなく、ブロック中→相談あり→進行中→未着手→完了 の順
5. **全体完了見込みを集約** … 各%の加重平均で「全体進捗の見立て」を1行表示

### フォーマットルール

- Markdown 記法（`#`, `*`, `**`, `>`, `-`, `` ` ``, `[]()`）は**一切使わない**
- 番号は `①②③④⑤…`（最大⑳）。それ以上は `(21)(22)…` にフォールバック
- 抽象タグ呼称は使わず**番号だけ**。「案件」「タスク」「項目」等の語は本文に出さない
- ステータスタグは `[完了]/[進行中]/[未着手]/[ブロック]/[保留]` の5種
- 詳細ブロックの行頭は `・`、根拠は `　　根拠：` でぶら下げ
- 区切り線は `━`、固有名詞は `「」` で括る（タイトル中は不要）
- 絵文字は使わない（記号 `■・━「」` のみで構造化）
- **会社名は本文に書かない**（送信側でメンション・宛先を付与する前提）

### 期日表記ルール（直感的に意味が伝わる形を必須化）

短縮記号（`【〜5/1】` のような形）は**禁止**。「これ何の期日？」と読み手に考えさせない。
**用途語＋日付＋曜日＋区切り** をフルで書く。

| 用途 | 推奨表記 |
|-----|---------|
| 自分の完了予定 | `完了予定 5/2（土）` ／ `5/2（土）までに完了見込み` |
| 相手からの回答が欲しい | `ご回答希望：5/1（金）中まで` |
| 相手の判断が欲しい | `ご判断希望：4/30（木）終業時刻まで` |
| 相手の確認が欲しい | `ご確認希望：5/1（金）中まで` |
| 共有が欲しい | `ご共有希望：5/1（金）中まで` |
| 既に完了 | `完了済` |

ルール:
- 必ず**曜日**を `（月）〜（日）` で併記（誤認防止）
- 「中まで」「終業時刻まで」「午前中まで」など**時間粒度**を明示
- ご相談の各サブ項目には**項目内2行目にぶら下げ**で書く（本文と期日を分離して読みやすく）
  ```
  1) 〜してください
  　 ご回答希望：5/1（金）中まで
  ```
- 終業時刻は `EOD` のような英略語ではなく `終業時刻まで` を使う（直感的）

### 複数要素の構造化（サブ箇条書き）

ご相談・残課題・次アクションは**複数あるのが標準**。1つしか無くても構造を崩さず以下の形を維持:

```
　・ご相談（N件）：
　　1) 〜してください
　　　 ご回答希望：M/D（曜）中まで
　　2) 〜をご教示ください
　　　 ご回答希望：M/D（曜）中まで
　・残（N件）：
　　1) 〜（所要 N.Nh）
　　2) 〜（所要 N.Nh）
```

ルール:
- 親見出しに `（N件）` を付け件数を明示
- サブは `1)` `2)` `3)` … の番号付き（順序＝対応してほしい順）
- ご相談は本文と期日を**2行に分け**、期日は `ご回答希望：M/D（曜）中まで` 等のフル表記
- 残課題には**各々に所要時間目安**を `（所要 N.Nh）` で付ける
- 1件しかない場合も `（1件）：` + `1) 〜` の構造を維持（書式統一のため）

### 二段構造（ヘッドライン＋詳細）の運用

- **ヘッドライン**：番号・タイトル（15文字以内）・ステータス・% を1行ずつ。N件あろうとここで全体把握できる
- **優先してほしいご判断**：意思決定要のものだけ抜粋（ヘッドライン直下に置く＝最重要を先頭に）
- **詳細**：番号順にステータス別の必要要素のみ展開
- **稼働時間**：末尾に1行

### 項目数による日報スリム化（読みにくさ抑制）

| 項目数 N | 詳細ブロックの扱い |
|---------|-----------------|
| N ≤ 3 | 全項目を詳細展開 |
| 4 ≤ N ≤ 7 | 完了項目は1行に圧縮（`本日：…／確率 100%`）。それ以外は通常展開 |
| N ≥ 8 | 完了は1行に圧縮、未着手は2行（残・確率のみ）に圧縮、進行中・ブロックのみフル展開 |

→ 全体見込み％は常に全項目の加重平均で算出（重みは均等。将来：期限近接度×重要度で重み付け拡張）

### 各項目内の記述順（受け手＝上司目線で重要度の高い順）

**固定順**:
1. **期限／確率（+ 根拠1行）** — 最重要。「本当にこの期日までに終わるのか」が先頭
2. **ご相談・確認事項** — 上司が判断・回答すべき項目
3. **残課題・次アクション** — 続きで何が残っているか
4. **本日の対応** — 当日の細かな実作業（最後）

受け手は上から順に読めば、関心の高い情報を先に得られる。本日対応は補助情報として末尾。

### ステータス別の必要要素（冗長排除・上記の順序を維持）

**項目見出し行に稼働時間を併記**:
`<番号> <タイトル>　[ステータス]　稼働 N.Nh`

| ステータス | 必要要素（記述順） |
|-----------|-----------------|
| 完了 | 見出し+稼働・期限／確率・本日（残・相談は省略可） |
| 進行中 | 見出し+稼働・期限／確率・（相談あれば）・残・本日 |
| 未着手 | 見出し+稼働(=0.0h)・期限／確率・（相談あれば）・残・本日（=着手なし） |
| ブロック | 見出し+稼働・期限／確率・**ご相談（必須）**・残・本日 |
| 保留 | 見出し+稼働・期限／確率・保留理由・残 |

### 項目の並び順（受け手が動くべき順に上から）

ヘッドライン・詳細とも同じ並び順:
1. **[ブロック]** — 上司の即決断が必要
2. **[進行中] かつ ご相談あり** — 判断待ち
3. **[未着手] かつ 期限近接（≤3日）** — 緊急未着手
4. **[進行中]** — 通常進行
5. **[未着手]** — 期限余裕あり
6. **[保留]** — 待機
7. **[完了]** — 報告のみ（最後）

### 完了確率の算出ガイドライン（AI 内部基準）

- 100%: 完了済 or 物理的に確実
- 80-95%: 進行中で順調・自分の手だけで完結
- 50-75%: 着手中だが他者依存・確認待ちあり
- 30-50%: 未着手で時間的制約あり、または難所残存
- 0-30%: ブロック要因未解消で進められない

→ AI は対話から数値候補を提案し**1行根拠を必ず添える**。人間が承認/微調整。

### 全体完了見込みの計算

- ヘッドライン1行目 `全体見込み NN%（M件平均）` は各項目％の単純平均
- 「稼働 Xh」と並記して**1行で全景**を伝える

### 稼働時間の項目別内訳

- 末尾「本日の稼働」ブロックは合計 + 項目別の2段構成
- 形式:
  ```
  ■ 本日の稼働
  　合計 Xh（HH:MM - HH:MM）
  　・① N.Nh
  　・② N.Nh
  ```
- 着手時間ゼロの項目（未着手など）も `0.0h（未着手）` で明示し抜けを防ぐ
- 0.5h単位で記録（ユーザー申告ベース。AI は推論しない）
- 合計と内訳の合算が一致しない場合は AI が警告を出す（齟齬検出）

## 7. 成功基準

- 1回の日報作成: 対話開始から `.txt` 生成完了まで **5分以内**
- Slack に貼った時に **見出し・箇条書きが崩れずそのまま読める**こと
- 受け取り手が「読みやすい」と言える簡潔さ（本文2000字以内目安）
- **読み手が1案件を上から下に追うだけで完了率まで把握できる**（複数ブロックを行ったり来たりさせない）
- 「優先してほしいご判断」ブロックを見れば、即返信すべき項目が3秒で特定できる
- 企業切替時に手動ミスがゼロ（自動列挙 + 確認）
- 3ヶ月運用で `_knowledge/` が成長し、トーン・用語の自動踏襲が機能している

## 9. 引き渡し条件（skill-creator 用）

- パターン: A（新規作成）
- 必要な機能ブロック:
  1. 企業選択 UI（自動列挙 + 新規追加。`_knowledge_*` で始まるファイル/エントリは除外）
  2. 対話による作業ログ収集
  3. 企業別ナレッジ JSON 群（`_knowledge_<企業>_*.json`）の一括読み込み・統合
  4. **Slack 直貼り用プレーンテキスト本体生成**（Markdown非使用・案件単位の縦束ね構造）
     - 本日サマリ（完了/進行中/未着手 件数 + 優先判断要請）
     - 案件①〜N（各案件: [ステータス] / 本日の対応 / 残課題・次アクション / ご相談・確認事項 / 期限／完了確率%）
     - 本日の稼働時間
     - 優先してほしいご判断（一覧再掲）
  5. **案件抽出器**: 対話ログから案件を識別し、各案件に5要素（ステータス・対応・残・相談・期限/確率）を埋める
  6. **完了確率推定器**: 進捗・依存・期限から AI が候補値を提案、人間が確定
  6. 概要タイトル候補提案 + 承認フロー
  7. ファイル名生成・保存（`YYYY-MM-DD_<概要>.md`）
  8. ナレッジ自動更新エンジン:
     - samples への append（承認された日報）
     - glossary への append 提案（新規用語検出）
     - feedback への append（指摘の構造化記録）
     - 500行超え検知 → 自動ローテーション（分割キー付与で新ファイル）
- 出力先制約: `05_Project/00_業務委託/00_作業日報/<企業>/` 配下のみ書き込み
- 認証情報・外部 API: 不要（完全ローカル）
