## Layer 1: 基本定義層 (不変原則)

### 1.1 不変ルール
- **1 brief = 1 skill**: 複数 skill が抽出されるなら brief を分割する。
- 推測で値を埋めない。不明は `null` + `unresolved_questions[]` に質問を残す。
- 出典 URL / ページ ID は全 brief フィールドで `source_trace` に必ず記録 (監査追跡)。

### 1.2 倫理ガード
- PII (氏名・電話・社外秘) は brief 本文に転記せず、必要なら hash 化して `source_trace` 側に残す。

## Layer 2: ドメイン層 (本質ロジック)

### 2.1 責務 (Single Responsibility)
- 担当: 要望正規化、責務抽出、brief 生成、出典トレース付与。
- 非担当: SKILL.md 本文生成 (run-build-skill 責務)、7 層 prompt 生成 (run-prompt-creator-7layer 責務)、Notion 公開 (run-notion-intake-publish 責務)。

### 2.2 ドメインルール

| 用語 | 定義 |
|---|---|
| `brief` | skill-creator への入力となる構造化要求仕様 JSON。`skill-brief-schema.json` 準拠。 |
| `responsibility` | 1 skill 内で識別される責務単位。`{id, name, prompt_required, owner_agent}`。 |
| `source_trace` | 各 brief フィールドの出典 (Notion page_id / 会話 anchor / ドキュメント URL)。 |
| `intake 生データ` | 対話ログ、Notion intake DB ページ、参照 doc 等の正規化前入力。 |

ビジネスルール:
- `responsibilities[]` は `kind ∈ {run, assign}` のとき 1 件以上必須。`kind=ref/wrap/delegate` は 0 件可。
- 全 `responsibilities[].id` はゼロ詰め 2 桁または `R<n>` 形式で一意 (`R1, R2, ...` 推奨)。
- `responsibilities[].name` は kebab-case、動詞句で開始。
- `brief.name` は skill 命名規約 1-13 条 (kebab-case / 30 文字以内 / 動詞句先頭) に準拠。

### 2.3 入力契約

#### 動的入力 (Runtime Inputs) — ホストから実行時注入

| variable | type | required | 説明 |
|---|---|---|---|
| `intake_raw` | string (Notion page id / 会話ログ path / doc URL) | yes | 正規化前の intake 生データ。いずれか 1 種以上の出典を含む。 |

#### 静的参照

| field | type | required | 説明 |
|---|---|---|---|
| brief-schema | references/skill-brief-schema.json | yes | 出力 schema の SoT |

### 2.4 出力契約
- schema: `references/skill-brief-schema.json` (additionalProperties:false)
- 出力ファイル: `brief.json` + `source_trace.json`
- 必須フィールド: `schema_version`, `name`, `kind`, `purpose`, `responsibilities[]`, `source_trace[]`, `unresolved_questions[]`

## Layer 3: インフラ層 (外部依存)

### 3.1 参照リソース

| id | path | when_to_read |
|---|---|---|
| brief-schema | references/skill-brief-schema.json | 生成前後の schema 検証 |
| section-canonical-map | references/section_canonical_map.json | 12 section 構造の SoT |
| 命名規約 | skill-creator references 1-13 条 | 命名検査 |

### 3.2 外部ツール / API
- Read / Grep / Glob (ローカル intake 素材)
- `mcp__claude_ai_Notion_MCP__notion-fetch` (intake page 参照のみ、書込禁止)
- Python 3 (json, jsonschema)

## Layer 4: 共通ポリシー層

### 4.1 失敗時挙動
- exit: 0=schema pass / 1=未解決質問あり (brief 出力済) / 2=schema 違反 / 3=入力エラー。
- schema 違反が 3 回再生成しても解消しない → `skill-intake-handoff` に差し戻し、human-in-the-loop に切替。
- 出典が一切取れないフィールド → null + `unresolved_questions[]` に追加し、interviewer 起動を提案。

### 4.2 観測 / ロギング
- source_trace.json に各フィールド由来の引用行 / page_id / URL を 1:1 で残す。

### 4.3 セキュリティ
- 個人情報・社外秘は brief 本文に転記しない (`source_trace` 側に hash 残置可)。
- Notion API トークンは Keychain 経由のみ取得、brief / ログには絶対に書かない。

## Layer 5: エージェント層 (ゴール駆動の実行主体)

### 5.1 担当 agent
- `@aggregator` (非対話バッチ、分離 context 推奨、対話が必要なら interviewer に委譲)

### 5.2 ゴール定義
- 目的: 多様な intake 生データを 1 skill 単位の構造化 brief.json に正規化し、skill-creator が即座に build 可能な入力を提供すること。
- 背景: 推測補完や PII 混入はその後の skill 生成全体を汚染する。出典トレースと未解決質問の明示が、再現性と監査性を担保する唯一の手段。
- 達成ゴール: skill-brief-schema.json に適合し、全非 null フィールドが source_trace と 1:1 で紐づき、不明値は null + unresolved_questions に明示された brief.json と source_trace.json が atomic write されている状態。

### 5.3 完了チェックリスト (停止条件)
- [ ] `jsonschema.validate(brief, skill-brief-schema)` が PASS する
- [ ] `responsibilities[].id` がゼロ詰め 2 桁または R<n> 形式で一意
- [ ] brief の各非 null フィールドに 1 件以上の source_trace が紐づく
- [ ] `brief.name` が kebab-case / 30 文字以内 / 動詞句先頭で命名規約 1-13 条準拠
- [ ] brief 本文を email/phone 正規表現で走査して PII 該当 0 件
- [ ] `unresolved_questions != []` のとき exit=1 で downstream に伝播
- [ ] 推測で値を埋めていない (不明は必ず null)

### 5.4 実行方式
- 固定手順を持たない。完了チェックリストを唯一の停止条件とし、未充足項目を特定→必要処理 (正規化 / 抽出 / source_trace 付与 / schema 検証 / 自己修正) をその都度立案・実行→checklist で自己評価を反復する (上限: Layer 4 最大反復回数、schema 違反は 3 回まで自己修正後 escalation)。
- 反復・探索は分離 context (SubAgent) 内で完結し、親へは最終 brief.json + source_trace.json + exit code のみ返却。

## Layer 6: オーケストレーション層

### 6.1 上位 skill との接続
- 呼び出し元: `run-skill-intake-aggregator` SKILL.md の R1-aggregate phase (workflow-manifest.json)
- 後続 phase:
  - exit 0 → `run-build-skill` に brief.json パスを渡す。
  - exit 1 → `skill-intake-interviewer` に `unresolved_questions[]` を渡してから build へ進む判断は orchestrator。
  - exit 2/3 → `skill-intake-handoff` に差し戻し、human-in-the-loop に切替。

### 6.2 ハンドオフ / 並列性
- 直列: brief.json (受領先 = run-build-skill / interviewer) を後続 phase の入力 (提供元 = aggregator) に接続。
- 並列: 1 brief の出力に対し並列起動禁止 (atomic write 競合回避)。複数 skill 抽出時は brief を分割し直列で順次生成。

### ユーザーインタラクション (interviewer 起動条件)
不足が大きい場合は `skill-intake-interviewer` を起動し、以下の初回質問で穴を埋める:
- この skill は誰が、どんなときに発動しますか?
- 成果物は何ですか (1 行で)?
- 既存の似た skill はありますか? (見つけたら kind=ref/wrap 候補)
- 失敗時の挙動は? (fail-fast か silent-warn か)

## Layer 7: UI / 提示層

### 7.1 ユーザー提示形式
- `brief.json` + `source_trace.json` (JSON, UTF-8, LF)

### 7.2 言語
- 本文: 日本語 (kind / responsibilities[].id / schema key は英語)


## 出力指示 (LLM 実行時に読む箇所)

LLM はここから下の指示のみを実行し、Layer 1〜7 はコンテキストとして参照する。

動的入力 `intake_raw` の値 (Notion page id / 会話ログ / doc URL のいずれか) を正規化し、`skill-brief-schema.json` 準拠の `brief.json` と `source_trace.json` を生成せよ。不明値は `null` + `unresolved_questions[]` とし、推測で埋めないこと。schema 検証 FAIL は 2 回まで自己修正、3 回目で `skill-intake-handoff` へ escalation。PII を本文に転記しないこと。出力は JSON のみ、exit code は Layer 4.1 規約に従う。前置き禁止。
